# Context Language Models (Meta FAIR / UW): context as a file the model edits with bash

Context Language Models ([arXiv:2609.37725v1](https://arxiv.org/abs/2609.37725), 2026-09-29, [HTML](https://arxiv.org/html/2609.37725); Shao, Shen, Yin, Li, Wang, Ivison, Poovendran, Lambert, Xiao, Lewis, Yih, Zettlemoyer, Koh — University of Washington, Meta Superintelligence Labs, MIT, Trillium Labs) redefines the LM context update itself: instead of appending generated tokens to a transcript the harness owns, the model owns the transcript and rewrites it.

The implementation is a mirror file the model edits with ordinary bash, synchronized back into the live context every turn. This report is grounded in the full paper (v1, the only version per the abs page, CC BY 4.0) and a code read of [facebookresearch/context-language-models](https://github.com/facebookresearch/context-language-models) shallow-cloned at HEAD `483198229ab7b90c0eed4651306ab3b3505aaf50` (2026-10-13, "Suffix Cache Reuse: put the SGLang and vLLM implementations side by side"); the repo is CC BY-NC 4.0. All repo-relative paths below are against the cloned HEAD. The round-trip unit tests pass locally at HEAD (`clm/tests/test_context_string.py`: 6 tests, 11 subtests).

## 1. What the paper proposes: context as a model-controlled transition

- A standard LM is append-only: `c_{t+1} = c_t ⊕ f^LM_θ(c_t)` (paper Eq. 1).
- A CLM defines the next context directly: `c_{t+1} = f^CLM_θ(c_t)` (Eq. 2), where `f^CLM_θ` "can be an arbitrary function controlled by CLMs". "Context language" in this paper names this transition function: the model's input at turn t+1 is whatever the model decided its context should be, not input-plus-appended-output.
- The subsumption claim: Eq. 2 covers prior context-management tools, because compaction/offload/retrieve tools are pre-defined pieces of `f^CLM_θ` the harness owns; a CLM "is responsible for defining these functions themselves as a meta-capability, either implicitly through their planning or explicitly as reusable functions" (§4.1, Fig. 3d shows an evolved helper `compact_turns(text)` reused 37 times).
- The framing is deliberately The Bitter Lesson (Sutton): unrestricted edits let the model search for strategies beyond human priors; the paper calls this "adaptive and creative context-management strategies" emerging zero-shot.
- Implementation core (§4.1): "mirror the LM's live context as a directly editable file and provide its path in the system prompt". Edits to the file are synchronized to the live context automatically; when the model does not edit it, generated tokens append normally.
- Multi-agent extension: "multiple context files can coexist and remain synchronized with their respective LLM servers"; subagents are initialized and terminated by creating and deleting context files (§4.1). In the released code this extension exists only as a trajectory format, not a runtime (section 3).
- Qualitative emergent behaviors (Fig. 3, from zero-shot runs): an orchestrator scoreboard maintained by 163 in-place edits while context stays at 6–8K tokens; a new chat role "notes" invented when rewriting; `re.sub` loops that strip irrelevant search results; reproduction of summary-compaction behaviors (21K tokens compressed into answer-relevant summaries plus preserved untried ideas for an exploration ledger).
- Cost is redefined, not hidden. Edits break prefix cache reuse, so the paper measures prefix-reuse FLOPs (Eq. 3, Appendix C): per turn, prefill of tokens from the first prefix mismatch onward plus decode — the trajectory-wide compute a prefix-caching server actually performs.

Pattern: the contribution is not a new model class — it is one extra degree of freedom in the harness (writable context) plus an honest cost metric for it.

## 2. Position against in-window prompting, action-based management, retrieval, and memory

The related-work section (§2, Appendix A) builds a spectrum; each step trades harness control for model control.

- Harness-defined management: Cursor, Codex, and Terminus2 (Terminal-bench's winner) trigger compaction at a predefined length with a prescribed summarization procedure. MEM1 rewrites context at every turn. RL can train models to survive these procedures (Composer, CompactionRL), but "the update schedule and procedure remain prescribed by the harness".
- Action-based management, in order of increasing model autonomy: AutoCompact and Self-Compact (model decides when to compact); Context-as-a-Tool (model-triggered compaction over a predefined portion of the context); ACM (adds offloading and retrieval); AgeMem (adds long-term memory operations plus summarize/filter tools); Context Folding (branch a sub-trajectory, fold it into a summary on return); AgentFold (folding directives that condense recent turns); Sculptor (fragment-level summarize/hide/restore/search preserving message count and order). The paper's verdict: "model autonomy increases but remains restricted to a human-defined action space". CLM's position: "Our work pushes this autonomy to its limit by granting the model full agency over its context" (§2).
- Standard in-window prompting is the control case: in the pilot, Mini-SWE-Agent is "the base harness without context management" — a normal append-only transcript that dies at the wall. CLM differs from it exactly by the writable mirror and by nothing else: same single-tool shape, same bash.
- Retrieval-augmented approaches are not the target category, and the paper says why. Appendix A: "The distinction depends on the role of the information, not its storage format. In CLMs, the context file specifies the input to subsequent model calls. Other files can serve as external memory, with their contents entering the context when retrieved. Making the live context editable therefore complements external memory by letting the model decide how retrieved information is incorporated and when it is removed." Memory-R1, MemGPT, and AgeMem are the named points of contact; MemGPT is the sharpest contrast — it lets the model edit a designated fixed-size memory block inside the context, while CLM edits the entire live context.
- On deep research the paper's "less-is-more design principle" applies to tools themselves: "Instead of training the agent against a fixed tool interface, we expose the search tools as in-context skills ... tools can be flexibly defined, added, or revised at inference time" (§5.1.1).
- The one prior line the paper treats as a sibling is the context-as-variable line (section 6).

Pattern: every constraint predecessor (thresholds, portions, fragments, schedules) becomes a special case of the writable context; the paper's contribution is collapsing that pattern language into one primitive.

## 3. The implementation: a mirror-file round trip

The released harness (`clm/clm_harness/`) is `ClmAgent` on the [Harbor](https://github.com/laude-institute/harbor) framework (`harbor==0.16.1`, `litellm`, `tiktoken`, `pyyaml`). One tool in the model's action space — bash (`clm/clm_harness/utils/tool_schemas.py`, `BASH_TOOL`). The module docstring states the design: "A single `bash` tool: no dedicated compaction tool" (`clm/clm_harness/clm_agent/harness.py:7-28`).

- **Turn cycle** (`context_env/env.py:182-258`): before each command the harness renders the editable region to `/tmp/.live_ctx/LIVE_CTX_MAIN.txt` in the sandbox (host-side staging file via `tempfile.mkstemp`, `env.py:68-70`; path constants `harness.py:103-105`), runs the one bash command in a persistent shell with a cwd/env snapshot-restore wrapper (`env.py:94-107`), downloads the file back, and if it changed maps it into the conversation.
- **Round-trip format** (`context_utils/context_string.py`): the editable region (turns after system prompt + task; `protect=2`, `harness.py:106`) renders as `[[CTX_TURN i role=assistant|user|tool]]` blocks. `parse_back` re-pins the protected prefix from the originals, recovers turns from whatever headers survive, turns stray leading text into a user note, drops emptied turns, and merges consecutive same-role turns.
- The deliberate loss: "History is reconstructed as plain role+text (tool-call structure is not preserved across an edit) — the price of 'edit the raw string however you like', and always legal" (`context_string.py:27-29`). The module is dependency-free and unit-tested.
- **Edit gate** (`context_env/edit_gate.py`): "fit" (default) accepts an edit that fits the enforced limit; "shrink" accepts only a strict reduction; a rejected edit is not applied and the model receives a frozen rejection note ("The rejection note is prompt text shown to the model; its wording must not change", `edit_gate.py:7-10`). Selected by agent kwarg or `CLM_EDIT_GATE`. The shipped BCP config uses `shrink` (`configs/bcp.yaml`); the ContextBench paper kwargs use `fit` (`clm/clm_contextbench/clm_stream.py:62`).
- **Budget machinery** (`utils/budget.py` — documented as one shared state machine, "deterministic gate / no mechanical truncation"): enforced limit is `context_budget_tokens − reserve` (2,048 default); one-shot nudges at 25/50/75% that fire once and re-arm after compaction; an adaptive persistent nudge firing every turn while headroom is below `max(10% of limit, 2× the largest of the last 3 tool outputs)`, never below 50% of the limit; a newest-output cap so one tool result cannot blow the budget.
- **On overflow**: rollback of the newest turns to a 2,048-token margin with a demanded compaction, repeated up to `max_num_retry_on_limit` (class default 50; 6 in the BCP config; 0 on ContextBench, where one final turn ends the run at the budget wall); after retries exhaust, one final turn, then the verifier grades the container as-is.
- **Tokenizer calibration**: the gate counts with tiktoken locally, then learns a ratio to the served tokenizer from real responses (`harness.py:577`, `budget.py:79-83`, env override `CLM_TOK_RATIO`).
- **Free editing turns**: a pure compaction (mirror changed, no stdout/stderr, exit code 0) consumes no task step (`ctx_turn_is_free`, `harness.py:127-130`) but still counts against `lm_call_cap` (default `2·max_steps + 24`), the bound that stops unbounded editing loops. This is the code counterpart of the paper's "CLM's editing turns do not count toward the turn limit" (Appendix E).
- **Rollback ledger**: a rollback erases the model's memory of what it just tried, so the harness pins a ledger message just after the protected prefix naming the last five overflow-causing commands, to prevent livelock (`harness.py:419-449`).
- **Status readout**: an unadvertised `context_status` call returns a live line with percentage used, free tokens, recent growth rate, and an estimated turns-of-headroom (`env.py:127-145`).
- **What the model reads vs what stays external**: everything the model is allowed to see is in the one context, and the prompt's first rule is "don't `cat` this file (its text is already in your context)" (`clm_agent/prompts.yaml:42`). There is no retrieval subsystem, no memory store, and no context-tool API; offloading is model-authored bash (the paper's ContextBench KV Store skill has the model move SET batches to `/tmp/ctx_offload/` and grep them back on demand). Observations are bounded only at 10,000 chars (head/tail 5,000/5,000; 60,000 in the BCP config, 50,000 on ContextBench) — tool outputs arrive essentially whole.
- **The system prompt teaches the cost model** (`prompts.yaml:16-58`): locate-by-code-never-retype editing, keep turn headers, don't retype removed text, and explicit economics: "an edit forces everything *after* it to be re-read, so cost grows with how much text FOLLOWS the edit — batch; mind what's below your edit; be generous in the summary: the tail is re-read regardless, so a detailed replacement is essentially free."
- **Not in this release: subagents and swarms.** The class rejects experimental kwargs as an error ("experimental features that are not part of this release ... so a stale launcher cannot run a different configuration from the one it names", `harness.py:108-124`) — the rejected list includes `subagents`, `n_subagent_slots`, `subagent_max_steps`, `subagent_lifetime_cap`, `subagent_self_compact`, `context_tool`, `research_ledger`, `unlimited_ctx_turns`. The trajectory format (`agent_trajectory_format/`, "ATIF-CTX v1") records subtrajectories with `spawn`/`fold` edges over `SUBCTX_<slot>` and `finished_subagents/` conventions (`models.py:219-244`) — multi-agent runs are observable, but the spawner itself is withheld.
- The Software World swarm ran in the Pi agent harness (Appendix E: "Every agent runs in the Pi agent harness with Pi's default model and context limit, GPT-5.6-Sol with a 272K-token context"), not in this repo's agent.
- **Day-1 integrations** (top-level `README.md:46-59`): a Pi plugin (`pi install npm:@lolipopshock/pi-clm`) and a community OpenCode port the authors do not maintain.
- Configuration is externalized in YAML (`configs/bcp.yaml`, `configs/edgebench.yaml`) expanded into `--agent-kwarg` flags by the `clm-harbor` CLI wrapper; runs emit `trajectory.json`, `usage.json`, `timing.json`, per-call `context_snapshots/`, and `trajectory.ctx.json`, with a `code_fingerprint` hash of the harness source in usage (`harness.py:689`) so runs can be matched to code.

Pattern: one data plane. The transcript is a file; there is no second store, no paging API, and none needed — the model and the harness see the same bytes.

## 4. Training/inference requirements: a harness first, learning second, serving third

CLM is primarily a harness protocol; the training contributions are optional layers on top, and the serving contribution answers the cost problem the protocol creates.

- **Zero-shot**: any OpenAI-compatible server with tool calling works (`clm/clm_harness/README.md:117-127`; Qwen served via vLLM with `--enable-auto-tool-choice --tool-call-parser qwen3_coder`). No fine-tuning is required for the headline zero-shot results.
- **One model-side concession**: the harness gives an editing reminder 2,048 tokens before the budget, explicitly framed as "temporary augmentation" because existing models score poorly on context-length estimation — models give bucketed estimates (6.2K, 9.8K, 10.4K) at length; Claude 4.6 Sonnet tends to underestimate; anchored hints help, and closer anchors help more (Appendix G). Future CLM training could internalize this signal.
- **In-context learning** (`clm/clm_icl/`): a skill is SKILL.md text appended to the system prompt (`harness.py:466-467`). The loop (`evolve.py`): run the current skill on training tasks → build a contrastive note (`note.py`: a success and failure of the same task, or two successes differing in cost, with step-indexed digests) → the proposer writes N full-rewrite candidates with a strict output contract, each citing episode id + step index ("cite the step or drop the lever", `proposer_prompt.md:43-46`) → malformed candidates are dropped, not repaired (`propose.py`) → candidates run on dev tasks → the gate replaces the incumbent when the mean-reward delta beats the paired standard error, or on a tie when cheaper, with ties-within-one-SE broken by cost (README "The gate"). State accumulates a Pareto frontier in `state.json`.
- The proposer may be a stronger model (assisted evolution) or the agent model itself (self-evolution); it sees only training-split rollouts, and the held-out test split is evaluated once after the archive freezes.
- **Reinforcement learning** (`clm/clm_rl/`): the training code is not released — the directory is a README plus two patches. The dual-channel advantage is `A[i,t] = r_i + w_eff · a_eff_i · m_i[t]`, where `m_i[t] = 1` only on tokens of turns whose sole action edits the context mirror, and `a_eff_i = clip((mean_flops − flops_i)/mean_flops, −1, 1)` computed within a rollout group over trajectories that solved the task cleanly; 0 when fewer than two successes; `w_eff = 0.25`. This realizes Eq. 6 with one refinement the paper does not spell out: the efficiency channel is token-masked to edit turns, while the outcome channel stays a plain group-normalized broadcast.
- The patch `0001-slime_bridge-dual-channel-advantage.patch` targets NVIDIA's ProRL-Agent-Server at `8bc67cc`; `0002-slime-forward-a_eff-and-role_masks.patch` targets Slime at `bf9b1a3`. The README warns the patches do not produce their own two required inputs (`sample.metadata["a_eff"]`, per-token `role_mask`) — reward post-processing and trajectory construction must supply them.
- Training configuration (paper Appendix E + README): Qwen3.5-9B; 3,040 OpenResearcher prompts, one epoch; 8 prompts × 32 rollouts per step; lr 1e-6 constant; weight decay 0.1; clipping [0.2, 0.28]; KL 0.01; 70 steps; reward penalties 0.3 (no tool call) and 0.2 (format failure) on failed trajectories; efficiency weight 0.25 applied to context-management tokens; 16 H200 GPUs for the policy + 48 for rollout generation; checkpoint selected on 500 held-out OpenResearcher questions.
- **Serving — Suffix Cache Reuse** (`suffix_cache_reuse/`): keeps the radix tree as-is and reuses KV for tokens that survive an edit. Per conversation, a session-private GPU side buffer holds the previous turn's KV (defaults: 12 sessions × 30,000 tokens ≈ 21.97 GiB at 64 KiB/token for Qwen3.6-27B). On each request it diffs the new prompt against the previous one and relocates up to K=6 surviving spans, largest-first: copies K/V into fresh slots, re-rotates RoPE keys to their new positions, splices them into the request's prefix, and always forwards at least the last 16 tokens of each span as real prefill (`KVREUSE_V6_MIN_EXTEND`) so linear-attention layers run on live tokens before the next spliced block.
- Hybrid models: for Qwen3.6-27B (48 of 64 layers are Gated DeltaNet), linear-attention layers maintain a recurrent state rather than per-token KV, so they cannot be relocated; SCR restores the recurrent state snapshotted at the end of the previous prompt at the first relocation (`KVREUSE_SSM_MODE=fork`) while the edit lands only in the 16 full-attention layers. Fallback: standard prefix caching when no plan applies or slots cannot be allocated; relocated entries live in session-private slots, so the shared radix tree never holds a moved entry.
- Implementation shape: a monkeypatch loaded into every SGLang process through a `sitecustomize.py` on `PYTHONPATH` — "no SGLang source file is modified" (SGLang 0.5.16, `suffix_cache_reuse/sglang/overlay.py`, ~1,935 lines); an independent vLLM 0.19.1 implementation sits on vLLM's scheduler and KV-connector extension points (`vllm/vllm_scr/{planner,scheduler,connector}.py`, design in `vllm/DESIGN.md`). Both share the same algorithm and knob names; K=6 is chosen by a 64-question sweep where gains saturate and accuracy is robust across K ∈ {1,2,3,6,12,64}.
- Session matching needs no protocol change on the agent side: conversations are keyed by content (longest common prefix ≥ 1,024 tokens plus high overlap) with optional per-request opt-out via `cache_salt: kvreuse:off`; `analysis/scr_report.py` derives per-request token splits (`radix_matched + relocated + forwarded`) and prefix-reuse PFLOPs from server logs, cross-checking totals two ways before reporting.

Pattern: measure the cost your freedom creates, then buy most of it back at the serving layer.

## 5. Benchmark results with linked numbers

- **ContextBench pilot** (4 synthetic tasks, GPT-5.4, 32K limit, pressure up to 24×; §3, Appendix D):
  - Tasks: Needle Retention (~4K-token chunks; 2–8 needle lines among 140 filler lines; metric = verbatim needle lines in the final context), Sudoku Sketchpad (16×16 board, one move per turn; metric = exact board reproduction per version), KV Store (batches of 100 SETs with random 24-word values; 24 GETs; exact-value accuracy), Log Triage (batches of 14–54 service log lines; 24 lookup/count queries; exact-answer accuracy).
  - All metrics are computed from the agent's context; "answers held only in files are not credited". Operations enter the context before the agent can act; the agent controls only pacing (`echo READY_FOR_NEXT_OP`). Budget design prevents unsolvable tasks: 30,720 usable tokens, one op ≤ 1/5 of it, required retention ≤ half, with 10% margins.
  - Every method receives a method-specific skill written to comparable detail (Table 4), so the pilot measures mechanism fit, not prompt effort.
  - Finding: "none of the existing methods performs perfectly even on these simple tasks" — summaries lose or hallucinate needles; methods without in-place editing regenerate the full Sudoku state per move; coding tools can offload but "cannot evict it from the live context on demand".
- **Terminal coding and deep research** (Qwen3.6-27B, 32K budget, all zero-shot on a shared Mini-SWE-Agent backbone; §5.1.1, Fig. 5):
  - BrowseComp-Plus: CLM 59.4%, "exceeding the strongest baseline, Codex-style summarization, by 11.4% relative", with 21.5% (vs summarization) and 28.9% (vs MEM1) fewer prefix-reuse FLOPs. Setup: all 830 questions, top-10 snippet search of 512 tokens, 8,192-token document reader, ≤4,096 generated tokens/call, rollback-and-retry up to six times, judged by Qwen3.5-27B at temperature 0.
  - TerminalBench 2.1 (89 tasks, verifier-graded): matches summarization while using only 70% of its prefix-reuse FLOPs (the abstract's "29.5% fewer").
  - TBLite: 73.7% vs 67.0% for summarization, with 91% of its FLOPs.
- **Mathematical optimization** (Claude 4.6 Sonnet, 32K, 100 scored attempts or five hours; Table 1, one run per method):
  - Circle packing: CLM 2.618 (CLM+subagents 2.636) vs OpenEvolve 2.541 and OpenEvolve-Agent 2.525.
  - Heilbronn triangle: CLM 0.03653 vs 0.03127 (+16.8%, the paper's "up to 16.8%").
  - Min-max/min-dist: CLM 0.07758 vs 0.07690. Erdős minimum overlap (lower better): CLM 0.38094 vs OpenEvolve 0.38123, OpenEvolve-Agent 0.38167.
  - The evolutionary workflow is provided as in-context guidance over the same base harness; "a general agent with direct context control can outperform a specialized evolutionary workflow with less fixed orchestration".
- **Long-horizon repository optimization** (§5.1.2):
  - EdgeBench-10 (10 of 48 public tasks, 12-hour containerized runs, 3 seeds): Qwen3.6-27B at 32K — CLM 44.6 using 179 prefix-reuse PFLOPs/trial vs summarization 42.3 using 437 (the abstract's "5% higher scores with 59% fewer FLOPs"); CLM+subagents 44.2 at 181. Claude 4.6 Sonnet: CLM 51.0, CLM+subagents 50.4 vs summarization 42.3.
  - At a 128K budget: CLM+subagents 50.2 (219 PFLOPs), CLM 47.3 (142), summarization 47.8 (222); the three context-managing methods keep improving over the full twelve hours while the base harness stops improving within the first two hours.
  - Observed: "subagents provide little additional benefit on this single-repository benchmark".
  - Software World (six agents over requests, urllib3, and four downstream packages, 24+ hours, GPT-5.6-Sol at 272K in the Pi harness): 65% greater downstream speedup on 17 held-out CPU benchmarks from four unseen packages at equal spend (a breaking benchmark counts as 1.0).
- **Steering by natural language** (Claude 4.6 Sonnet on BCP questions, one appended sentence per behavior; §5.2, Fig. 9): compacting when context crosses 16K/24K/32K moves the median first-compaction point; compacting at sub-question boundaries raises boundary-adjacent compaction (189 paired sessions, 131 with an internal boundary); mandatory pre-edit backups raise the backup rate (91 paired questions). All three measured with paired BCa intervals; "without any change to the harness or model parameters".
- **Skill evolution** (ContextBench, 32K; §5.2, Fig. 10, Appendix F):
  - Assisted evolution (Qwen3.6-27B agent, Claude Fable 5.1 proposer) raises development-split accuracy from 97.6 to 100.0 (Needle Retention), 45.3 to 65.8 (Sudoku), 22.3 to 83.8 (KV Store), and 0.0 to 100.0 (Log Triage). The held-out KV Store skill goes 38.3 to 74.2 — the abstract's "up to 35.9 points" — at lower compute.
  - Self-evolution (Opus 5 as both agent and proposer) starts at 94–100% and converges on cost reduction at equal or higher accuracy.
  - Protocol: each candidate runs 6 training instances (then 12 more if at frontier), is selected on a 102-instance dev split with 1 seed, and the frozen archive's best skill runs once on 102 test instances × 3 seeds; four parallel proposers, each reading ≥10 rollouts, ≥4 full rewrites; a lineage stops after 5 consecutive non-improving proposals; frontier membership requires no prior skill to be at least as accurate and at least as cheap.
- **RL** (Table 2, BrowseComp-Plus, Qwen3.5-9B pre/post the same 70-step recipe): summary harness 34.7 → 42.1 at 4.01 → 2.19 PFLOPs/question; CLM 28.8 → 42.5 at 1.52 → 1.34. Before training, small-model CLM trails the summary harness by six points; after training it leads by 0.4 points with 38.8% fewer FLOPs. The abstract's "+47.6% while using 12% fewer FLOPs" is the CLM row (accuracy 28.8 → 42.5, cost 1.52 → 1.34 PFLOPs); "the efficiency reward further reduces inference cost without a clear loss in accuracy for either CLM or the summary harness".
- **SCR serving** (Qwen3.6-27B on BCP): paper §5.3 — matched accuracy at 65.0% of standard SGLang's empirical prefix-reuse FLOPs; the repo README's three-seed numbers are 60.6% (SCR) vs 59.0% (standard) accuracy at 65.5% FLOPs. Reasoning-strip decomposition: of the 7.8% of prompt tokens SCR reuses beyond prefix-cache hits, the paper attributes 5.3 points to stripped reasoning tokens and 2.5 to context edits (repo README: 5.4 and 2.4) — i.e., most of SCR's benefit applies to standard reasoning-model serving without any context editing. vLLM implementation: −24.7% prefix-reuse FLOPs per question and −12.5% time per question at accuracy 58.88% vs 58.80% over all 830 questions.

## 6. Relationship to the context-as-variable line

- **RLM ([arXiv:2512.24601](https://arxiv.org/abs/2512.24601), Zhang, Kraska, Khattab)** is the closest relative and the named complement. RLM (paper read in full, v1) loads a long input as a REPL variable the model reads programmatically and decomposes via recursive sub-calls of itself; strong results at 10M+ token inputs (e.g., RLM(GPT-5) 91.33% on BrowseComp-Plus-1K vs 70.47% summarization). Its live interaction context remains a normal growing transcript.
  - The CLM paper's Appendix A states the distinction in two parts: "RLMs externalize the input rather than the evolving interaction history, and the model's access to its live context remains read-only rather than read–write ... The two approaches are complementary: RLM-style access can keep large inputs outside the context until needed, while CLMs can manage the information brought into the context and the history generated while processing it."
  - From §2: "However, RLMs do not address how the live context itself should be managed. Retrieved information is still appended to the live context, which continues to grow over time. In contrast, our work makes the live context editable."
  - RLM is an evaluated baseline in both the pilot and the main experiments (shared Mini-SWE-Agent backbone; "RLM runs its released harness"); in ContextBench its REPL namespace is framed as the store, with the same fetch-and-answer discipline as CLM's grep-based offloading (Table 4).
- **[NOOA](nooa.md) ([arXiv:2607.20709](https://arxiv.org/abs/2607.20709))** sits at the opposite end of the same axis.
  - NOOA keeps the transcript append-only and cache-stable by construction and moves state into live Python values the transcript only previews, so compaction becomes unnecessary at reported token levels. Its single model-callable transcript operation is a range-collapse (`events.collapse("2", "40", summary)`), with compressed originals remaining addressable by tag.
  - CLM generalizes that one constrained operation into arbitrary bash edits of the whole transcript, and pays the cost NOOA's architecture never incurs: mid-context writes invalidate the KV prefix. The prefix-reuse FLOPs metric exists precisely to price what NOOA avoids by projection budgeting; SCR is the co-designed partial refund.
  - The two papers also differ in the unit of control: NOOA's boundaries are types (typed previews, typed fields, snapshot-serializable durability); CLM's is a file with a restoration contract (headers preserved, tool-call structure surrendered).
- **Continual Harness ([arXiv:2605.09998](https://arxiv.org/abs/2605.09998), abstract read)** refines harness state — prompt, sub-agents, skills, memory — online, review-gated, within one run, starting from a minimal environment interface.
  - CLM's skill-evolution loop optimizes one text skill (a single SKILL.md) through an offline train/dev/test loop with an explicit Pareto gate. The paper states the shared goal directly: "Our skill evolution therefore shares the goal of harness optimization: improving reusable context-management procedures through evaluation feedback" (Appendix A).
  - The divergence is in what gets optimized and where it acts: Continual Harness improves procedures that then drive the agent's context from the outside (its harness store is model-callable state); CLM keeps the harness frozen, puts the procedure both in the skill text and in the model's own edit behavior, and treats weight-level internalization (RL) as the endpoint.
  - CLM's §6 framing of harnesses as "a form of procedural memory or task-specific skill that can be developed externally and later absorbed by CLMs" is the direct bridge to that line of work — and to [prime-agent.md](prime-agent.md), whose Continual Harness report records review-gated refinement as the safety mechanism CLM's skill gate solves differently (statistical acceptance gate rather than LLM review).
- **Prime Agent ([arXiv:2608.23552](https://arxiv.org/abs/2608.23552))** productizes RLM's half of the split: context-as-kernel-variable with bounded ingress (64 KiB host-side), persistent namespace, `rlm.spawn` subagents. CLM's release converges with that line from the other direction only in integration: the day-1 Pi plugin turns Pi's harness into a CLM, while Prime keeps its context append-only with threshold compaction — the harness-defined end of CLM's own spectrum.

## 7. Failure modes and limits

- **Security** is named by the paper itself (§6): an editable context is a persistence channel for prompt injections, including self-generated ones; it cites an OpenAI misalignment report (2026-09) on injections surviving inside compaction summaries, and calls for defenses "that preserve the flexibility of model-controlled context while maintaining its integrity".
- **The capability assumes a good model.** Qwen3.5-9B without training edits its context much less (1.4 edits/task on TerminalBench 2.1, no edit at all in half the tasks, median peak 30.2K of the 32K limit) than Qwen3.6-27B (2.6 edits/task, 17.6K median peak), and pre-training CLM at 9B trails the summary harness (28.8 vs 34.7 on BCP). "CLM leaves the decision of when and how to edit the context to the model, so its gains grow with the model's ability to make that decision" (Appendix F). The harness transfers the whole management problem to policy quality.
- **Edits are never free under prefix caching.** The system prompt has to teach the trade (batch edits, mind the tail below the edit, generous summaries), and the FLOPs accounting exists precisely because unrestricted editing can be more expensive than the compaction it replaces — the pilot's methods that edit without cost-awareness lose on both axes.
- **The round trip is lossy by design.** Tool-call structure does not survive edits (`context_string.py:27-29`); the edited region can only be reconstructed as plain role+text. The harness guarantees legality, not byte fidelity. Consequences are unexplored in the paper — e.g., how provider-side parity checks or reasoning-block stripping interact with reconstructed histories beyond the one footnote about Qwen3.6/GPT-5.6 chat templates.
- **"Unrestricted" is bounded by harness machinery.** The edit gate rejects edits (fit/shrink); rollback-retry permanently discards turns from the trajectory (only a retry count records them, `budget.py:19-22`); free-edit turns count against `lm_call_cap`; observations are head/tail truncated. The paper's framing ("full agency") describes the tool space, not these retention guards.
- **SCR is an approximation.** Reused KV was computed under the pre-edit prefix — deliberately "stale" cache the paper argues can even help — and each relocation adds approximation that can compound before the model adapts in later turns; K=6 bounds the damage per edit and captures most gains. The remaining waste is a serving-stack limitation: SGLang stores hybrid linear-attention recurrent states only at cached request boundaries, so unchanged-prefix reuse can fall back to a much shorter prefix — marked as an implementation limitation affecting standard prefix caching too.
- **The efficiency metric is a model of serving, not wall-clock.** Prefix-reuse FLOPs are computed from token sequences; the harness replays ordered per-turn context snapshots through a prefix trie or uses exact server `cached_tokens` when available (`flops_metrics/kv_cache_flops.py`; N_BODY = 6.9196×10⁹ for "9b", 24.3532×10⁹ for "27b"; the O(L²) attention term is added when model geometry is resolvable and materially increases the measured cost of long contexts). The vLLM result (−12.5% time per question) is the one directly wall-clock-measured claim in the release.

## 9. Open questions and uncertainties

- Enforced-limit arithmetic does not reconcile across artifacts: `configs/bcp.yaml` sets `context_budget_tokens=28672` (comment: "32768-token window minus max_tokens") with a 2,048 reserve, giving a strict target of 26,624 — while paper Appendix E states a 23,560-token budget for BCP. Served-tokenizer calibration could account for part of the gap, but the mapping is not stated anywhere.
- The same config says `max_steps: 500` for BCP while the paper says 100 turns (the config comment says 100, 500 and 2000 "were all used"); the paper also omits that the shipped BCP config retains 0.25/0.5/0.75 nudges and a 0.9 persistent nudge, mentioning only the 2,048-token editing reminder.
- Small numeric drift between paper and repository: SCR FLOPs share 65.0% (paper) vs 65.5% (repo, three-seed average); reasoning-strip split 5.3/2.5 (paper) vs 5.4/2.4 (repo), both out of 7.8% — likely different run subsets or rounding stage, not stated.
- The paper's §4.2 advantage statement ("assign each trajectory's advantage to all of its constituent segments") and the released token-masked dual-channel form differ in scope; whether the trained runs used exactly the released mask shape is documented only in the README.
- Whether the pilot-study and main benchmarks' baseline skills were tuned beyond what Table 4 discloses cannot be verified from this repo, since the baseline harnesses live in external repositories.
- The Pi plugin (`@lolipopshock/pi-clm`) and the OpenCode port are outside this repository; their implementation quality and maintenance status were not audited here.
- License asymmetry: the paper text is CC BY 4.0; the repository is CC BY-NC 4.0 — reuse bounds differ between the paper's claims and the code.
- ContextBench itself is a separate repository ([RulinShao/ContextBench](https://github.com/RulinShao/ContextBench), tasks mirrored on HuggingFace); its grader implementation was not audited for this report.
- The mirror-file propagation costs (upload/download per turn, 10K-char observation caps at class defaults vs 60K in BCP) are harness-side overheads the paper's FLOPs model does not include; their magnitude in practice is unknown from the paper.
