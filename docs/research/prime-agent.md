# Prime Agent: A Self-Improving RLM Harness

## Summary

Prime Agent (Prime Intellect, https://github.com/PrimeIntellect-ai/prime-agent) is an open-source coding and research agent harness for long-horizon work, built around two abstractions: the Recursive Language Model (RLM), which makes the model's context a programmable object inside a persistent Python kernel, and the Continual Harness, which stores supplemental prompts, memories, skills, and subagent specifications as durable, versioned state refined from trajectory evidence. This report was upgraded from paper/blog reading to code analysis: the Rust workspace and the embedded `prime-agent-runtime` Python package were cloned (shallow clone at HEAD `3e141d105ccd2b3b267436b0fa4c6011a2c37d19`) and read as the primary source. Code reading confirmed the paper's architectural claims, corrected several of the blog's implementation details (section 11), and surfaced mechanisms the paper and repo docs never describe: reusable state-machine factories over spawned children, a quiescence-based completion contract, a daemon-owned spawn ledger preserving family topology across passivation, orphan-process journaling, and a review-gated auto-refine pass after every compaction (section 10). Section 12 derives what baton-cli should adopt; section 13 states the core architectural concepts the design optimizes for.

## 2. Architecture at a glance

The crate layout is a layered microkernel: `pa-types` is the only shared vocabulary crate; `pa-agent` is a provider-independent agent loop; `pa-core` owns the session engine, tools, skills, and kernel; `pa-daemon` owns the supervisor, workers, and wire protocol; `pa-tui` renders from wire types only; `pa-cli` is a composition root with no business logic (`crates/AGENTS.md` — the crates table and dependency rules; `crates/pa-cli/README.md`).

**Pattern: one engine, several surfaces over one wire.** Every user-facing surface is a client of the daemon wire. The TUI is a "daemon-wire client" (`crates/AGENTS.md` crates table), headless RPC runs over the same protocol, and ACP (Agent Client Protocol) stdio mode is "served over a daemon session" with a jsonrpc translation layer (`crates/pa-daemon/src/acp/mod.rs:1-6`). The model-visible machinery lives once in `pa-core`/`pa-daemon`; adding a surface means adding a wire client.

The single most load-bearing code decision: the model-facing tool surface is one tool. The base prompt layer states it directly: "The prime-agent harness has one tool: `python_repl`, a persistent CPython REPL. All other tools are 'programmatic tools', functions inside the Python REPL called via 'programmatic tool calling' (PTC)" (`crates/pa-core/src/prompts/layers/core.md:3`). The session engine guarantees `python_repl` is registered by appending it when config omits it (`crates/pa-core/src/session_engine/engine.rs:485-496`); other loop-visible tools come from configuration (`config.tools.clone()`, same block). Note: `crates/AGENTS.md` ("Surface contract") still lists `bash`, `edit`, `python_repl` as exposed tools — the code keeps `bash`/`edit` as replayable built-in tool names for TS parity (`crates/pa-core/src/tools/tool_definition.rs:109-111`), and `active_tool_names` can include `bash` in some modes (`crates/pa-core/src/session_engine/engine.rs:586`), but the prompt the model sees declares the one-tool surface.

## 3. Context as a variable: the kernel and programmatic tool calling

**Pattern: context-as-variable kernel.** Every session owns a persistent CPython kernel (`crates/pa-core/src/kernel/` — `manager/`, `provisioner.rs`, `bootstrap/`). At kernel start or restore, the session injects a bootstrap cell that binds the `rlm`, `bash`, and MCP surfaces and pre-imports every Python skill (`crates/pa-core/src/kernel/bootstrap/runtime_code.rs:33-174`). The surfaces come from the `prime-agent-runtime` package (`prime-agent-runtime/src/rlm/__init__.py`); if it is missing, a stub object raises with repair instructions instead of failing the session (`runtime_code.rs:45-73`).

**Pattern: bounded result ingress.** The kernel serializes REPL execution results to at most 1,048,576 characters with an explicit truncation marker (`prime-agent-runtime/src/rlm/repl.py:51-56`); the host applies a smaller per-execution cap, `DEFAULT_MAX_OUTPUT_CHARS = 65_536`, overridable per request via `max_output_chars` (`crates/pa-core/src/kernel/shared.rs:12`, `crates/pa-core/src/kernel/manager/requests.rs:151`). This is the concrete form of context-as-variable: large data stays in kernel variables, and what enters the model's context is a capped projection the model must query programmatically.

**Pattern: kernel as a versioned JSON-lines subprocess.** The kernel is not a library: the host runs it as `python -m rlm.repl`, a JSON-lines subprocess taking requests on stdin, emitting events on stdout, and keeping stderr as a diagnostics tail; the wire protocol is versioned (version 3) and documented in `prime-agent-runtime/src/rlm/repl.md` (`crates/pa-core/src/kernel/manager/mod.rs:1-5`). A per-session provisioner owns one kernel manager, guards its startup, revives the saved namespace before the runtime bootstrap runs, and disposes or kills on demand; reader tasks hold weak references so no kernel outlives its provisioner, and `dispose()` flushes the snapshot first (`crates/pa-core/src/kernel/provisioner.rs:1-4`). A process-wide live-kernel registry enforces exactly-once disposal at shutdown with a flush-then-teardown ordering (`crates/pa-core/src/kernel/live_kernels.rs:1-4`).

**Pattern: background-first concurrency.** The prompt's usage layer instructs the model to run bash commands in the background without awaiting them and collect results in a later `python_repl` call — "blocking calls reduce user responsiveness" — while very short commands may be awaited directly; the harness sends a notification when a command finishes (`crates/pa-core/src/prompts/layers/usage.md:8`). Combined with `BashHandle` awaitability after completion (`core.md:9-18`), tool execution is asynchronous by default and the model synchronizes only where it chooses to.

**Pattern: durable user namespace.** The kernel's user namespace is persisted per-variable and revived on session resume ("best-effort and per-variable: a single unpicklable object is skipped and reported, never aborting the whole snapshot"; 256 MiB total ceiling, 16 MiB per-variable skip) (`crates/pa-core/src/kernel/state_snapshot.rs:1-9`). Compaction likewise "removes individual variables whose serialized form exceeds 16 MiB" (`crates/pa-core/src/prompts/layers/core.md:139`). State survives as data the model can address, not as a transcript blob.

Programmatic tools available in the REPL (signatures from `crates/pa-core/src/prompts/layers/core.md:7-25` and the kernel bridge `crates/pa-core/src/session_engine/rlm_host.rs`): `bash(command) -> BashHandle` (synchronous call that starts a background process; the handle is awaitable after completion and supports `.tail()`, `.output()`, `.poll()`, `.kill()`), `edit.run(path, old_str, new_str)`, `websearch.run(query)`, `attach_image(*paths)`, MCP tools (`mcp.call_tool(server, tool, arguments)` with runtime-discovered schemas, `core.md:161-171`), and executable skills pre-imported as modules callable with `await <skill>(...)` (`core.md:173-177`).

## 4. Recursive subagents

**Pattern: spawn-as-admission with results by message.** `rlm.spawn(prompt, *, name, model, thinking)` "spawns a new subagent one level deeper than the caller; returns immediately; ... results never arrive as `rlm.spawn()` return values, they arrive only via agent_message" (`crates/pa-core/src/prompts/layers/core.md:33`). The Python side sends a typed host request; the Rust side validates shape locally (name length ≤ 64 chars, thinking level, model reference) and hands spawning to the child-session host (`crates/pa-core/src/session_engine/rlm_host.rs:1-10`; `crates/pa-core/src/kernel/rlm_runtime.rs:48-139`). `RlmSpawnHandle { rlm_child_id, name, session_dir, model }` is "returned once the child task is admitted" (`rlm_host.rs:25-31`). On the daemon, `RlmSubagentHost` implements the wire surface `spawn`, `create_session`, `list_subagents`, `delete_subagent`, `collect`, `rename` over the supervisor's child-sessions registry, with a depth gate and enforced child-model allowlist (`crates/pa-daemon/src/rlm_children/host.rs:1-4,58-62`; `resolve_child_model_allowlisted`).

**Depth bound.** `DEFAULT_RLM_MAX_DEPTH: u32 = 2` (`crates/pa-core/src/session_engine/rlm_host.rs:265`), overridable via environment or global settings; the engine stamps the bound's source (`default | env | global`, `crates/pa-daemon/src/agent_engine/lifecycle.rs:189`). This resolves the open question from the paper-era report: default recursion depth is 2, not 1.

**Sibling sessions and renames.** `rlm.create_session(prompt, name, model, thinking, cwd)` creates another depth-0 session and is available only to agents at depth 0 backed by a daemon; it "returns after the session is successfully created and the first prompt sent", and its handle carries both a live `active_session_id` and the durable `session_id` with the on-disk `session_file` path (`crates/pa-core/src/prompts/layers/core.md:34,46-51`). `rlm.rename` renames the calling session or a direct child, enforces sibling-name uniqueness, and appends a transcript line to the renamed session (`core.md:38`); spawn-name reservations are guarded so a name cannot be double-admitted (`crates/pa-daemon/src/rlm_children/host.rs` imports — `SpawnNameReservationGuard`, `spawn_name_unavailable_error`).

**Child results and statuses.** A spawned child's handle status is `running | completed | error`, with live detail (current activity, tool-use count, duration, answer preview, latest progress note) attached to roster rows (`core.md:52-59`). `rlm.collect(targets, timeout_ms)` returns typed snapshots without steering anyone; a positive timeout blocks only that call until children settle or the deadline passes (`core.md:39`). `rlm.progress_note(message)` reports in-flight progress to the parent, hard-capped at 512 characters and throttled to one note per 10 seconds (`rlm_host.rs:22-23`; `core.md:40`).

**Session lifecycle.** Roster status is the three-state enum `AgentRosterStatus { Running, Idle, Inactive }` classified from a live-residency input plus queued-child flags (`crates/pa-types/src/daemon/agent_roster.rs:13-32`). The daemon passivates idle workers and keeps non-resident children visible through a separate ledger (next paragraph); a child stays marked running while any descendant runs, and idle passivation settles back to running if a queued prompt is admitted (`crates/pa-daemon/src/rlm_children/lifecycle.rs:339-341,472-476`).

**Pattern: family topology as a durable ledger.** Family topology (parent/child edges, depths, names) is not re-derived from session files. The supervisor appends spawn/rename/delete admissions to one append-only JSONL file per sessions dir, and every roster surface reads topology back from that file "so historical and non-resident children stay roster-visible after passivation" (`crates/pa-daemon/src/rlm_ledger.rs:1-8`). This is why spawned children survive parent death and daemon restart: children are supervisor-owned, not kernel-owned.

**Pattern: quiescence as the completion contract.** "A run completes at quiescence: no state entry in flight (pending/running/waiting) and no unevaluated settle" (`prime-agent-runtime/src/rlm/factory.py:1500`). The headless-completion wait `waitForRlmQuiescence` owns the parent's idle, then every admitted descendant run's settlement, looping back through the idle wait because work may start at a child-settlement boundary (`crates/pa-daemon/tests/rlm_quiescence_barrier_e2e.rs:1-5`).

**Undocumented mechanism: state-machine factories.** The `factory` harness kind (see section 6) is executable orchestration: `FactoryExecutor` "runs canonicalized state-machine factories through the existing RLM supervisor" — admission enters every entry state, each child settle is queued and its outgoing transitions evaluated once (fan-out is legal; a self-loop re-enters with freshly re-bound inputs), and the run completes at quiescence. Runs live in kernel memory and do not survive a kernel restart, but the children do, so `rlm.list_subagents` can still see and stop them (`prime-agent-runtime/src/rlm/factory.py:1487-1505`). The paper and blog never mention factories; they are the concrete embodiment of the paper's "programmatic orchestration" claim.

**Communication.** `agent_message.send(message, *, receiver_role: parent|sibling|child, receiver_name)` returns a receipt with a delivery status of delivered or queued; broadcast sends to the family roster (`core.md:68`; `AgentMessageDeliveryStatus::Delivered|Queued` at `crates/pa-daemon/src/agent_messaging/message.rs:408-412`). Agent messages are persisted into the session file as custom entries of type `agent_message` (`crates/pa-core/src/session_engine/agent_messaging.rs:6-9`), which is how queued messages survive recipient passivation. `agent_observe` exposes bounded read-only family status and transcript previews (`core.md:69-71`).

**The harness message protocol.** The runtime addresses the agent with structured user messages: "These are user messages starting with `[<kind>(: <qualifier>)( <address>)]` followed by a newline and then the content. They are not user-generated" (`crates/pa-core/src/prompts/layers/core.md:5`). The prompt documents that refinement notifications and background-work completions arrive as these harness messages (`core.md:83`; `crates/pa-core/src/prompts/layers/usage.md:8`), so the agent's model sees one message syntax for all system-originated input.

## 5. Subtree accounting

**Pattern: usage folded into the spawning row.** The producer "folds a recursive child's billable usage into the parent assistant row that spawned it" (`crates/pa-core/src/session_engine/rlm_usage.rs:1-4`); because Rust children are separate worker processes, the daemon's children registry delivers usage batches to the parent's session store, which appends idempotent child-usage attribution rows — "one durable row per stable row identity, written through the same persist core as every other row" (`crates/pa-daemon/src/session_store/child_usage.rs:1-3`). Delegation cost is therefore visible in the transcript itself, per spawn, not in a side report.

## 6. The Continual Harness

**Pattern: typed versioned state store with event-sourced refinement history.** The kernel-side store is deliberately small: `HarnessKind = "prompt" | "memory" | "skill" | "subagent" | "factory"`, session-local by default with an explicit `global_=True` cross-session scope, persisted as `harness_state.json` with a lock-dir scheme that syncs from disk before writes and detects dead owners (`prime-agent-runtime/src/rlm/harness.py:3-7,34-39,489-540`). Every entry carries an integer `version` "starting at 1" that increments with every update (`harness.py:210`, `core.md:123`). Skills additionally require a Python reference (`{"type": "python", import, callable/call_pattern}`) validated at write time (`harness.py:229-245,352-363`).

**Refinement flow.** Two triggers: the user command `/refine`, or the agent calling `refine.run(instructions)` — which "returns immediately and runs when the current turn ends" (`core.md:79-91`). The Rust side implements the flow as plan, then re-read, then apply, then persist (`crates/pa-core/src/session_engine/refine.rs:1-4`), with the executor splitting "rollback or LLM pass" proposals: a rollback references a prior refinement id, is stamped `rollback_of`/`rollback_scope`, and is applied as a proposal against the re-read store (`crates/pa-core/src/refinement/executor.rs:1-5,203-216`). Every refinement is recorded as a `RefinementEvent { id, trigger, changes, evidence, outcome, created_at }` whose persisted shape is validated to keep the store digest stable (`harness.py:215,380-397`; `core.md:129-135`).

**Review-gated auto-refine.** Every successful compaction arms an auto-refine trigger. The servicing order is explicit: "gates first, then the review, and only an approving review runs the refinement" (`crates/pa-core/src/session_engine/auto_refine_trigger.rs:1-4`). The daemon services the trigger off each turn's settle in a background task rather than inline, "the inline-before-`Done` shape held the next prompt behind the whole review" (`crates/pa-daemon/src/compact_autorefine.rs:1-4`). A master setting `harness_refinements` gates scheduling, planning, apply, and context delivery as the single live policy read (`crates/pa-core/src/session_engine/refinement_gate.rs:1-8`).

**Delivery into context.** The runtime composes the continual-harness state into a model-facing `[harness-digest]` user message and delivers it at cold context boundaries — session start, resume, and the head after compaction (`crates/pa-core/src/session_engine/harness_digest.rs:1-4`; the prompt's layer structure with a separate `[harness-digest]` message is also the surface contract in `crates/AGENTS.md`).

## 7. Daemon-backed sessions

**Windowed reads.** Transcript reads go through a windowed path that materializes only the active window's messages and reports the omitted count and last user-prompt timestamp (`crates/pa-daemon/src/session_store.rs:110-124`); a per-session window cache sits in front of it (`crates/pa-core/src/session/window_cache.rs`). Reading a session is incremental, which matters for the long histories the paper's multi-day runs produce.

**Pattern: process-per-session supervision over an append-only event tree.** The supervisor is "one process spawning one worker per active session: clients connect over a JSONL Unix socket; the supervisor spawns a dedicated worker per session, supervises it (restart with backoff, bounded attempts), and persists worker descriptors so a restarted supervisor can adopt live sessions" (`crates/pa-daemon/src/supervisor.rs:1-6`). Sessions persist as `{session_id}.jsonl` in the sessions dir (`crates/pa-daemon/src/session_store/read.rs:18`).

**Session event format.** A stored entry is an open envelope: `{ type: string, id, parentId?, timestamp, ...fields }` where "fields beyond the entry envelope are preserved as raw JSON" (`crates/pa-daemon/src/session_store.rs:95-108`). Agent messages ride the same file as `agent_message` custom entries (`crates/pa-core/src/session_engine/agent_messaging.rs:6-9`); compaction writes its own start/end event pairs (`crates/pa-daemon/src/compaction.rs:76-78`); child-usage attribution has its own row type (section 5). A separate semantic-edge ledger — "durable per-session append-only log of model-request events... one `O_APPEND` write per event, no fsync" (`crates/pa-core/src/session_engine/semantic_edges/ledger.rs:2`) — indexes the model-request view. The transcript window tolerates torn-tail damage at the append boundary by reopening after the last good record (`crates/pa-core/src/session/window_cache.rs:202`).

**Recovery.** Fork/branch creates a new logical continuation without deleting prior events; the supervisor adopts sessions after restart via persisted worker descriptors (`supervisor.rs:4-6`), and idle passivation with graceful stop plus replacement-worker monitoring covers worker death (`crates/pa-daemon/src/supervisor_roster/passivation.rs:1-3`).

## 8. Compaction

**Thresholds.** Two compaction numbers coexist and were both verified: the automatic trigger is a context-fill percentage with default 95 and valid range 1–100 (`crates/pa-core/src/settings/interactive_settings.rs:26-33`; `crates/pa-types/src/compaction.rs:1-5`), and the effective trigger reserves a token floor — "compacts automatically when there is only a given number of tokens left in the context window (default: 16384)" (`core.md:139`).

**Machinery.** Compaction runs are either manual (`compact` command) or automatic; both interrupt the running turn first, emit `compaction_start`/`compaction_end` event frames, and append a compaction entry to the session store (`crates/pa-daemon/src/compaction.rs:1-4,55-78`). One abort slot per session covers the manual run and the automatic run (`compaction.rs:16-17`). A compaction journal guards the append path: "a lost compact falls back to the append-only history" (`crates/pa-daemon/src/journal.rs:73`), so a compaction lost mid-flight degrades to a longer replay rather than lost state. After every successful compaction the auto-refine trigger is armed (section 6).

## 9. Mechanisms the paper and repo docs never mention

- **Factories** (`prime-agent-runtime/src/rlm/factory.py:1487-1505`, section 4): stored, canonicalized state machines whose states spawn RLM children and whose transitions fire on settlement; the `factory` harness kind (`harness.py:34`) makes an orchestration graph itself a versioned, refinable harness entry.
- **Quiescence barrier** (`crates/pa-daemon/tests/rlm_quiescence_barrier_e2e.rs:1-5`; `factory.py:1500`): completion is defined as no in-flight entry and no unevaluated settle, with re-entry through idle because children may start work at settlement boundaries.
- **Spawn ledger** (`crates/pa-daemon/src/rlm_ledger.rs:1-8`, section 4): family topology as its own append-only log, decoupled from session files, mirroring the TS record grammar with the divergence that replay skips a malformed line instead of failing the whole read.
- **Orphan-process journal** (`crates/pa-core/src/kernel/orphan_journal.rs:1-4`): the runtime journals every `bash()` process group under the kernel pid; the host reaps those groups when a killed or crashed kernel cannot run its own shutdown hook.
- **Destructive-git guard** (`crates/pa-core/src/tools/bash_guard.rs:1-10`): bash calls that would discard uncommitted changes are refused with a dirty-tree listing (up to 10 paths), with an explicit bypass environment variable.
- **Per-file mutation queues** (`crates/pa-core/src/tools/file_mutation_queue.rs:1-5`): file mutations targeting the same file (after symlink resolution) run in arrival order while different files run in parallel.
- **Child-model allowlist** (`crates/pa-daemon/src/rlm_children/host.rs:30-45`): `rlm.spawn` child models are resolved against a daemon `allowedModels` allowlist, refusing loudly with a typed error and a `model refused` event.
- **Quota parking** (`crates/pa-daemon/src/agent_engine/turn/quota.rs:1-7`): when a provider hits its usage limit, the engine parks the session with durable park/resume entries and wakes it on the `waitForUsage` retry policy, with bounded wake-recovery retries.

## 10. Corrections to the paper and blog record

- **The blog's 8,192-character cap is not in the product.** The verifiers-era RLMEnv truncated REPL output shown to the model at 8,192 characters (`https://www.primeintellect.ai/blog/rlm`). The product's host-side per-execution cap is 65,536 (`crates/pa-core/src/kernel/shared.rs:12`) and the kernel-side cap is 1 MiB (`prime-agent-runtime/src/rlm/repl.py:53`). The number 8,192 does appear in the product as `ANSWER_BINDING_CAP`, a preview cap for captured child answers in the factory machinery (`prime-agent-runtime/src/rlm/factory.py:1016`).
- **No `answer` variable, no `llm_batch`.** The blog's `answer = {"content": "", "ready": False}` protocol and `llm_batch` parallel sub-LLM calls belong to the verifiers `RLMEnv` training scaffold (`https://github.com/PrimeIntellect-ai/verifiers/blob/main/verifiers/envs/experimental/rlm_env.py`), not to the Prime Agent product. No `answer` variable or `llm_batch` exists anywhere in the cloned code; answers arrive via `agent_message` and typed `rlm.collect` snapshots (section 4).
- **The model-facing surface is one tool, not three.** `crates/AGENTS.md` ("Surface contract") lists `bash`, `edit`, `python_repl`; the shipped prompt layer (`core.md:3`) and the engine's guaranteed-registration of only `python_repl` (`crates/pa-core/src/session_engine/engine.rs:485-496`) present a single kernel tool with bash/edit as programmatic tools inside it.
- **Depth is 2 by default, not 1.** The blog's depth-exactly-1 limitation described the verifiers scaffold; the product's `DEFAULT_RLM_MAX_DEPTH` is 2 and configurable (`crates/pa-core/src/session_engine/rlm_host.rs:265`).
- **Refinement is more guarded than the paper describes.** Beyond versioned rollback, compaction-triggered auto-refinement runs only "an approving review" before applying (`auto_refine_trigger.rs:1-4`), is separately gated by a master setting (`refinement_gate.rs:1-8`), and refinement events carry evidence and outcome fields with digest-validated shapes (`harness.py:380-397`) — the code-level answer to the paper's Factorio exploit-preserved-as-skill failure (paper §3.5).
- **The `factory` harness kind extends the four types** the paper lists (prompt notes, memories, skills, subagent specs) with executable orchestration machines (`harness.py:34-39`).
- **Paper-reported outcomes (secondary source, not code-verified).** For completeness, the paper reports: ARC-AGI-3 RHAE Best@1 raised from 30% to 95.5% in its test-time-scaling configuration; an 85.5-hour nanoGPT speedrun with 19 verified records; and a seven-day Factorio run where the root created 633 depth-one subagents across 149 dispatch waves with at most seven concurrent, completing 24 of 196 technologies with 23.4 million output tokens. The paper notes uncertainty intervals are unavailable and its Claude Code/Codex ARC-AGI-3 reruns fell below vendor-published scores ([paper §3.1–§3.5](https://arxiv.org/html/2608.23552v1)).

## 11. Relevance to baton-cli

### 11.1 Patterns worth adopting

- **Append-only event envelope with fork-by-prefix.** `{type, id, parentId, timestamp, ...raw fields}` per line (`session_store.rs:95-108`) is a session format that records turns, tool calls, tool outputs, messages, compactions, and attribution as discrete events while staying open-ended. It matches baton-cli's plan for resuming and forking a seat at turn boundaries, and the code shows the needed adjacents: a topology ledger so spawn relationships survive restart (`rlm_ledger.rs`), torn-tail tolerance (`window_cache.rs`), and fork as a new continuation rather than a copy (`semantic_edges.rs`).
- **Spawn-as-admission plus results-by-message.** `rlm.spawn` returning an admission handle while results travel only through persisted message entries (`core.md:33`; `agent_messaging.rs:6-9`) is the cleanest way to make asynchronous tool execution default-safe: no half-completed return value, receipts distinguish delivered from queued, and the queue outlives the recipient (`crates/pa-daemon/src/agent_messaging/message.rs:408-412`). This is directly compatible with baton-cli's orchestrator inbox and default-async tool execution.
- **Quiescence as the completion contract.** Defining completion over "no in-flight entry and no unevaluated settle" (`factory.py:1500`) is how an orchestrator can settle a seat with background work without polling; baton-cli's completion-request protocol should adopt the same contract.
- **Typed versioned harness state with review-gated refinement.** The four-plus-one kind split, integer versions, local-by-default scope, evidence-and-outcome-bearing refinement events, and apply-only-after-approving-review auto-refine (`harness.py`; `auto_refine_trigger.rs`) are the strongest tested answer to the durable-state question baton-cli faces; the review gate is what makes auto-refinement safe enough to leave on.
- **Durable park/resume on provider quota.** When a provider hits its usage limit, the engine parks the session with durable park/resume entries and wakes it later on the configured `waitForUsage` policy, with bounded wake-recovery retries (`crates/pa-daemon/src/agent_engine/turn/quota.rs:1-7`); goals can carry a token budget that the engine enforces (`core.md:146-150`). An orchestrator allocating seats should own the same mechanism — park a seat on quota, resume on budget reset — rather than failing the seat.

- **Subtree accounting folded into the transcript** (`rlm_usage.rs:1-4`): attribution rows in the parent session file keep delegation cost visible where the session is read, which an orchestrator allocating budgets across seats needs.
- **A typed JSON-lines protocol between harness and kernel** (`crates/pa-core/src/kernel/manager/mod.rs:1-5`; protocol v3 documented in `prime-agent-runtime/src/rlm/repl.md`): the tool runtime is a subprocess speaking a versioned request/event protocol, which is what makes the kernel disposable, snapshot-able, and restartable. baton-cli's tool executor (or seat worker) should have the same seam: a documented protocol version between the harness core and whatever executes tools, so execution can crash and revive without corrupting the session.

### 11.2 What fits poorly for a minimal orchestrator-driven seat

- **The Python kernel as the only tool.** The kernel brings a venv provisioner, snapshot/revival machinery, orphan journals, and per-variable persistence (sections 3, 9) — a second runtime to operate. baton-cli's read/write/edit/shell tool set with the orchestrator as the coordination plane needs none of it; Prime Agent pays this cost to get PTC expressivity, which baton-cli is not targeting.
- **Model-side decomposition.** Spawn, factories, and family broadcast put decomposition in the model's hands (`core.md:27-40`). baton-cli places orchestration in the Bend2 orchestrator; giving seats spawn-like primitives would bypass the orchestrator's admission, accounting, and task structure. The factory system's kernel-memory registry (runs die with the kernel, children keep running) also shows the model-side split is awkward around recovery — exactly the boundary an orchestrator-owned design avoids.
- **Full self-improvement surface.** Global-scope entries, agent-callable refinement, and skill packages that pre-import into every kernel (`harness.py`; `core.md:173-177`) are heavy and trust-demanding; the code's own guards (review gate, master switch, digest-validated events) exist because the model can write harmful refinements. baton-cli should adopt the state-store shape with orchestrator-side validation before adopting the write surface.

### 11.3 Programmatic subagents as a research direction

The code supports the paper's claim that programmatic orchestration works in practice, but through two mechanisms the paper did not name: factories (deterministic state machines over spawned children) and quiescence-settled runs. For baton-cli, the research direction translates to exposing spawn/message/settle as ordinary calls in the seat's language while the orchestrator keeps admission and accounting — the factory executor's ownership split ("the supervisor owns the children... this executor owns the run state in kernel memory", `factory.py:1489-1492`) is a prior version of exactly that boundary, with the orchestrator taking the supervisor's side.

## 12. Core architectural concepts

1. **Context as a queryable variable.** The design moves information management out of prompts and into a persistent kernel: large data lives in variables, the model queries it in code, and only capped projections enter context (`repl.py:51-56`; `kernel/shared.rs:12`; `state_snapshot.rs`). The harness optimizes for a model whose effective context is what it can retrieve, not what fits in the window.
2. **One kernel tool, everything programmatic.** A single `python_repl` tool plus PTC (`core.md:3`) makes the tool-call surface composable — loops, batched subagent calls, and background handles in one cell — at the cost of a full Python runtime per session. The design optimizes for expressivity over tool-count minimality.
3. **Spawning as admission; results as durable messages.** Children are admitted (depth gate, allowlist, name uniqueness) and communicate through persisted `agent_message` entries in the session file (`rlm_host.rs:25-31`; `agent_messaging.rs:6-9`). The design optimizes for coordination that survives passivation, restart, and detach.
4. **Everything durable is an append-only log; identity survives as the tree.** Sessions, semantic edges, spawn topology, and refinement history are each append-only JSONL (`session_store.rs`; `semantic_edges/ledger.rs`; `rlm_ledger.rs`; `harness.py`). Fork-by-prefix and adoption-from-descriptors make restart a replay, not a rebuild. The design optimizes for recovery and auditability.
5. **Refinement as reviewed, versioned, evidence-backed commits.** Harness state changes only at turn boundaries, through gated plans that record trigger/evidence/outcome and can be rolled back by id (`refine.rs:1-4`; `executor.rs:203-216`; `auto_refine_trigger.rs:1-4`). The design optimizes for self-improvement that stays auditable.
6. **Process-per-session supervision.** One worker per active session with backoff restarts, passivation, and descriptor-based adoption (`supervisor.rs:1-6`; `passivation.rs`) isolates failures at the cost of process churn. The design optimizes for long-horizon resilience over resource economy.
