# Addressing and authority: prior art for cross-session context navigation

This report covers the addressing + authority half of the five missing primitives recorded in [context-networking.md](context-networking.md) §3.3: cross-session addressing, read grants for context reads, deref read budgets, passivation consistency, and shared live context. It reads five bodies of prior art — object-capability systems, macaroon credentials, Git/Datomic/CRDT versioned storage, the blackboard architecture, and Plan 9 namespaces — and maps each mechanism onto baton's landed substrate: content-addressed cells `cell:<sha256>` (64 MB ceiling), version-CAS bindings `(scope, name) → cell` with per-`(runId, scope)` fences, the citation grammar `repl:<scope>:<name>@<version>` with resolve-against-recorded-history ("never latest"), the principal-pinned `ReplManifest {runId, replRole}` as the admission-time authority record, server-minted grants on the `claimGrant`/`mintMemberBoardGrant` pattern, and the one-attachment wake plane. Method: each mechanism is read from its primary source (papers fetched in full; PDFs where machine-extraction succeeded), with per-claim links; extraction failures and unverified specifics are marked in §8.

## 1. Object-capability systems

### 1.1 The core model: unforgeable, delegable, revocable via parents

In seL4, a capability is "an unforgeable token that references a specific kernel object ... and carries access rights that control what methods may be invoked" ([seL4 Reference Manual 15.0.0](https://sel4.systems/Info/Docs/seL4-manual-15.0.0.pdf), §2.2); every kernel service is invoked only through a capability with sufficient rights (§2.1). Three operations carry the authority model:

- **Mint** (`seL4_CNode_Mint`) creates a derived capability with a subset of the source's rights; requesting more rights than the source has is silently downgraded to the source's rights (§3.1.4, §10.3.1.4). Mint can also attach a *badge*, a data word the invoker chooses; when a message is sent on a badged endpoint capability, the kernel transfers the badge into the receiver's badge register so a server can distinguish clients (§4.2.1). Badged capabilities cannot be unbadged, rebadged, or used to mint children with different badges.
- **Derivation tracking.** The kernel maintains a capability derivation tree (CDT) recording children produced by Retype, Mint, Copy, and Mutate (§2.4.1, §3.1.5). Derivation is type-restricted: some capability types cannot derive at all, and untyped capabilities copied always create children, never siblings.
- **Revoke** (`seL4_CNode_Revoke`) deletes all CDT children of a capability and leaves the capability itself intact; if a revoked child was the last capability to an object, the object is destroyed (§3.2, §10.3.1.7). Revocation therefore propagates down a parent's entire delegation subtree in one kernel operation.

KeyKOS established this shape earlier: a persistent, pure capability system on S/370, with a small nanokernel and whole-system checkpointing providing transparent persistence ([Hardy, "The KeyKOS Architecture", ACM OSR 19(4), 1985](https://pdos.csail.mit.edu/6.828/2008/readings/keykos.pdf); [KeyKOS notes at cap-lore.com](http://cap-lore.com/CapTheory/upenn/)). EROS demonstrated that the KeyKOS capability-plus-persistence model runs on commodity hardware with IPC performance comparable to conventional systems ([Shapiro, Smith, Farber, "EROS: a fast capability system", SOSP 1999](https://flint.cs.yale.edu/cs428/doc/eros.pdf)). Levy's survey is the standard taxonomy reference ([Capability-Based Computer Systems, 1984](https://homes.cs.washington.edu/~levy/capabook/)).

Two further properties of this lineage matter for the grant design. Persistence: KeyKOS checkpointed whole-system state periodically and EROS kept the same single-level-store discipline, so a capability outlived its process and a machine restart; the passivation-consistency question (§6, question 4) is the same problem one layer up — the durable object survives, the live process does not. Confinement: preventing a holder from re-delegating authority is treated in the capability literature as a property distinct from unforgeability, argued separately ([Miller, Yee, Shapiro, "Capability Myths Demolished", cited from the Cap'n Proto documentation as the standard treatment](http://zesty.ca/capmyths/usenix.pdf)). A per-deref non-transferable read grant is therefore asking for confinement, not capability discipline alone; the mechanisms that deliver it in the record are server-side minting plus channel binding, with the capability supplying the addressing and attenuation.

### 1.2 Capabilities as the addressing layer: Cap'n Proto

Cap'n Proto's RPC treats "interface references — or, as we more commonly call them, capabilities — as a first-class type": a capability "both designates an object to call and confers permission to call it" ([RPC protocol doc](https://capnproto.org/rpc.html)). Unforgeability is enforced by construction: the host assigns each object an ID specific to the connection over which it was sent, so third parties cannot access the capability without the host's or receiver's consent. Two protocol levels matter for cross-session design. Level 2 adds *persistent capabilities*: a client may "save" a capability to a token and "restore" it on a later connection, with the host deciding which capabilities are persistable. Level 3 adds *three-way introduction*: if Alice passes Bob a reference to Carol, machine B forms a direct connection to machine C so Bob calls Carol without proxying through Alice. Disconnection is a first-class outcome: when a connection drops, every capability served by it becomes disconnected and later calls throw typed exceptions.

The disconnect rule is the passivation precedent: a capability is scoped to its connection, and connection death is a typed outcome the client must handle, not a silent dangling reference ([RPC protocol doc](https://capnproto.org/rpc.html), "Handling disconnects"). Persisting a grant across connections is opt-in (Level 2) and per-capability, with the host deciding which capabilities are restorable. A baton grant that must survive seat passivation sits at the same design point: the default is scope-to-attachment — the one-attachment wake plane already scopes subscriptions to a single upstream attachment ([context-networking.md](context-networking.md) §2.2) — and persistence is a declared property of the grant, not a global default.

### 1.3 What minting a per-deref read grant gains and loses

Against this 40-year record, minting a non-transferable read grant per dereference gains attenuation, lineage, and revocation — and loses the classic capability model's cheapest enforcement property:

- **Gained — attenuation with monotone rights.** seL4's mint-with-subset rule (§3.1.4) is exactly the invariant a per-deref grant wants: a read grant for `worker:seat-a:findings@17` can never exceed the minting authority's rights over that binding. The silent-downgrade rule removes a whole class of grant-shape bugs.
- **Gained — revocation with a defined closure.** CDT-based revoke deletes the derived subtree in one operation (§3.2). A baton grant tree minted by the orchestrator would give the run owner a single revoke operation covering every grant derived from one admission — semantics baton's claimGrant pattern currently lacks, since its grants are closed server-side objects with no recorded derivation relation.
- **Gained — badges as principal pinning.** The badge mechanism (§4.2.1) is the same shape as baton's manifest-principal pinning: the mint stamps an unforgeable identity word onto the derived capability, and the kernel (orchestrator) delivers it to the receiver.
- **Lost — possession-based enforcement cannot make a capability non-transferable.** In every system above, authority follows possession: once the grant is delivered, the holder may pass it on (that is the model's delegation feature; Cap'n Proto makes passing it the whole point). Non-transferability is not a capability-system mechanism; seL4 badges identify but do not restrict transfer. The published remedy is macaroons (§1.4), which concede bearer transferability and add contextual caveats plus third-party discharge instead — or transport binding, where the grant is minted server-side against a specific session's channel and the enforcing server checks the requesting channel. baton's `claimGrant` is already the second form: the grant exists server-side before delivery, and the delivered worker fact carries no lease material ([context-networking.md](context-networking.md) §2.2). The cap-system lesson is that this non-transferability must be enforced at the deref boundary by the minting service, not assumed from the token's opacity.
- **Lost — cheap local invocation.** A kernel capability is checked in-kernel on a nanosecond path. An orchestrator-minted grant is checked over a protocol round trip per deref; the deref budget (§6, question 1) pays this tax.
- **Gained — per-object addressing granularity.** A seL4 capability addresses one kernel object, not a class of objects; a per-binding grant inherits the least-privilege default. baton's admission already pins scope, name, and version at the binding level, so a grant minted per binding version is the same granularity expressed at the protocol layer.
- **Lost — management cost moves to the minting side.** seL4 "requires the programmer to manage all in-kernel data structures, including CSpaces, from userspace" ([manual](https://sel4.systems/Info/Docs/seL4-manual-15.0.0.pdf) §3.1). Translated to baton: grant bookkeeping — slots, derivation records, revocation state — becomes orchestrator-side durable state with its own digest basis, which the current grant shape (closed, per-claim, stateless between claim and delivery) does not carry.

### 1.4 Macaroons: attenuation plus contextual confinement

Macaroons ([Birgisson, Politz, Erlingsson, Taly, Vrable, Lentczner, NDSS 2014](https://www.ndss-symposium.org/wp-content/uploads/2017/09/04_3_1.pdf)) are bearer credentials built from nested chained HMACs: each macaroon carries a key identifier and a chain of HMAC values in which each value is the key for the next message, so verifying integrity and establishing keys with derived macaroons is one construction (§I, §III). Three mechanisms map directly onto deref grants:

- **Caveats as attenuation and contextual confinement.** Caveats are predicates "that restrict the macaroon's authority, as well as the context in which it may be successfully used" (§I). First-party caveats are evaluated by the target service "in the context of each particular request" (§II.A) — e.g. `operation == read`, a chunk-range restriction, a validity period.
- **Third-party caveats with discharge.** A macaroon can require holder-of-key proofs from a named third party, discharged by a separate (possibly very short-lived) macaroon the target verifies recursively (§II.A, §III). The paper's running example is exactly the cross-service case: a forum service derives a read-only, single-chunk, IP-confined macaroon from its own authority and delegates authentication to an unrelated service.
- **Revocation strategies.** The paper names four: very short-lived credentials, freshness constraints, external authoritative state (revocation lists, epoch counters), and credential splitting (§II). It also states the construction's limitation plainly: HMAC macaroons "are verifiable only by the target service" (§II).

The paper's Figure 2 names the three patterns an intermediary has for giving a client limited access: proxy the requests, have the target service mint new restricted credentials, or derive a new macaroon from the one the intermediary already holds ([paper](https://www.ndss-symposium.org/wp-content/uploads/2017/09/04_3_1.pdf) §II). baton's `claimGrant` is the second pattern — the orchestrator asks the store to mint — and the paper's argument for the third pattern is that deriving a caveated credential directly removes the latency, transparency loss, and trust requirements of the re-minting path. The motivating use case (§I) is the same shape as cross-session navigation: the holder of private content at one service shares read access with members of a group maintained at an unrelated service, safely.

Mapping: a baton deref grant is a macaroon minted by the orchestrator with caveats `run == R`, `binding == (scope, name)`, `version <= V`, `budget_bytes <= B`, `expiry == T`; the wake-plane ledger-seq cursor and per-scope fences are the "external authoritative state" revocation channel. The open delta is §6, question 1: whether non-transferability is a first-party caveat (a channel check) or a third-party discharge against the seat's admission record.

## 2. Distributed versioned storage as the addressing layer

### 2.1 Git: content addressing plus refs as CAS bindings

Git "is a content-addressable filesystem ... a simple key-value data store" where inserting content returns a key computed over a typed header plus the content ([Pro Git §10.2](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)). Objects are blobs (content), trees (name→object entries with modes), and commits (tree pointer plus parents and metadata). Names for mutable work live in refs: "these simple names are called 'references' or 'refs'; you can find the files that contain those SHA-1 values in the `.git/refs` directory"; a branch is "a simple pointer or reference to the head of a line of work", updated by `update-ref`; HEAD is a symbolic reference that must stay within `refs/` ([Pro Git §10.3](https://git-scm.com/book/en/v2/Git-Internals-Git-References)). Tags are refs that "never move" — annotated tags wrap the target in a new object carrying tagger, date, and message.

The isomorphism with baton is exact at three points: cell ≡ blob (content-addressed immutable value, identified by hash); binding ≡ ref (`(scope, name) → cell` is a file of the same shape, `rebind` mints `bindingVersion + 1` under a CAS exactly as `update-ref` overwrites the ref file); citation `repl:<scope>:<name>@<version>` ≡ tag (a fixed pointer into binding history, playing the role the tag object plays for commits). Two deltas are load-bearing. First, Git refs are unauthenticated mutable files — Git's transfer security comes from signed tags and out-of-band trust, not from the ref mechanism; baton's binding digests (`H(scope, name, bindingVersion, state, cellId)`) move the authentication into the binding itself, which is the correction a networked design needs. Second, Git has no authority model at all: possession of the repository is possession of every object; any per-reader restriction is out-of-band. Git is therefore evidence for the addressing half and neutral on the authority half.

Two further Git mechanisms complete the mapping. The commit object is the binding history: a chain of immutable snapshots, each pointing at its parent and carrying author and message metadata ([Pro Git §10.2](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)). baton's per-key binding history with recorded versions is the same chain without the parent links; a cross-session navigation protocol that wants to diff or replay another seat's context line wants exactly the parent chain Git commits provide, so whether baton's binding history should record predecessor versions explicitly is a design question the Git model answers affirmatively. Reachability-based garbage collection is Git's retention rule: objects unreachable from refs and tags become collectible. baton's cell store retains admitted cells under its own rules, and a cross-run namespace adds a new reachability edge — a live citation from another run — that the current run-scoped design does not have to consider and the cross-run design must.

### 2.2 Datomic and event sourcing: immutable facts, as-of reads, derived projections

Datomic's data model ([docs](https://docs.datomic.com/data-model.html)): a database is "a set of immutable atomic facts called *datoms*", each a five-tuple of entity, attribute, value, transaction, and add/retract operation; "a db is a point-in-time, immutable value and will never change. If you use the same db for several queries, you will know the answers are based upon exactly the same data from a single point in time." The time model assigns every transaction a unique, totally ordered id; every datom carries its transaction; `:db/txInstant` gives wall-clock time; and "Datomic's time model allows complete recovery of the data 'as of' any point in time." Retraction is a new datom, not a deletion — corrections reference the transaction they correct. Event sourcing states the same shape as a pattern: state changes are recorded as a sequence of events and current state is derived by replay ([Fowler, "Event Sourcing"](https://martinfowler.com/eaaDev/EventSourcing.html)).

Mapping: baton's binding history is the log; a deref against `@<version>` is an as-of read; the replay-exactness requirement in [context-networking.md](context-networking.md) §5.1 (a dereference returns the exact bytes the author committed) is Datomic's point-in-time-value property restated for cells. Datomic also supplies the consistency answer for passivation (§6, question 4): a reader never needs the target session to be alive, because every read is against an immutable database value at a recorded transaction. The delta: Datomic orders everything through one transaction lane; baton orders per `(runId, scope)` with fences — the shared-scope lane is single-writer (orchestrator authority) while worker lanes are single-writer per worker, so the global total order Datomic guarantees is not present and derefs across two scopes have no defined cross-lane snapshot.

Datomic's indexes are the derived-projection half of the same model: the docs state that Datalog queries "automatically use multiple indexes to support a variety of access patterns" ([docs](https://docs.datomic.com/data-model.html)). baton's fence-keyed projection caches are derived projections over binding history, and every rebind bumps the per-`(runId, scope)` fence and invalidates them ([context-networking.md](context-networking.md) §2.3). A networked read that derefs another seat's binding inherits the same projection-invalidation economics as a local one, which is where the commit-cadence question in [context-networking.md](context-networking.md) §6 lands: the prior-art lesson is that projections are cheap only while their log input is quiescent.

### 2.3 CRDTs: convergence, and whether it is wanted

The CRDT result ([Shapiro, Preguiça, Baquero, Zawirski, SSS 2011](https://gsd.di.uminho.pt/members/cbm/members/cbm/ps/sss2011.pdf); extended as [INRIA RR-7687](https://hal.inria.fr/inria-00609399/document)) defines strong eventual consistency: replicas that have received the same updates converge to equivalent state without coordination, via either state-based types whose merge is a join-semilattice (CvRDTs) or operation-based types whose concurrent operations commute (CmRDTs); the report gives constructions for counters, sets (including observed-remove sets), graphs, and sequences.

What CRDTs would add to baton is narrow and conditional. They matter only where two sessions must converge on one *shared derived* object — a jointly maintained index, scoreboard, or merged brief — without an orchestrator round trip per write. baton's current objects make the opposite choice: cells are immutable, scopes single-writer, writes settled through admission, and reads version-pinned, so "convergence" is replaced by "each reader cites the version it resolved." Convergence is not obviously wanted: a merged state has no single author or version, which breaks replay-exactness and the provenance discipline baton applies to worker-authored content ([context-networking.md](context-networking.md) §4.2). The honest CRDT contribution is a fallback design for missing primitive 5 (shared live context with independent writers): accept concurrent writes, define merge as a lattice join, and mint each merge result as a *new cell* with a recorded merge event — which restores provenance and versioning at the cost of making every concurrent write eventually visible rather than adjudicated. Whether the adjudication baton performs (fences, single-writer scopes) is worth its coordination cost at swarm scale is unmeasured in every surveyed system ([context-networking.md](context-networking.md) §3.2).

If the fallback is taken, the type choice is constrained by the corpus's needs. An append-only shared index over committed cells is a grow-only structure — monotone insertion of `(cell, origin)` pairs — the class the CRDT report treats as the simplest CvRDT ([SSS 2011](https://gsd.di.uminho.pt/members/cbm/members/cbm/ps/sss2011.pdf)). Deletions and re-scoring of shared entries require observed-remove or add-wins semantics, whose merge results are no longer replay-exact by construction. No surveyed agent system uses CRDTs for context state: the corpus's shared stores are single-writer or orchestrator-arbitrated ([context-networking.md](context-networking.md) §3.2-§3.3), so the fallback is a design option with no published agent-era precedent, recorded as such.

## 3. The blackboard architecture

The blackboard model ([Nii, "The Blackboard Model of Problem Solving and the Evolution of Blackboard Architectures", AI Magazine 7(2), 1986](https://ojs.aaai.org/aimagazine/index.php/aimagazine/article/view/537), DOI 10.1609/aimag.v7i2.537) generalizes Hearsay-II ([Erman, Hayes-Roth, Lesser, Reddy, ACM Computing Surveys 12(2), 1980](https://dl.acm.org/doi/10.1145/358810.358836); [PDF mirror](http://faculty.chas.uni.edu/~wallingf/teaching/162/readings/hearsay-ii.pdf)). The framework has three components: knowledge sources, a blackboard data structure, and a control component. Knowledge sources are independent specialists that cannot call each other; they read and write a single structured global database whose levels hold partial solutions, and a control component decides which knowledge source executes next based on the board's state (Hearsay-II description corroborated across the sources above; the Hearsay-II PDF body did not survive text extraction — see §8). The model's load-bearing mechanisms, all directly ancestral to shared-context navigation:

- **Arbitration of concurrent contributors.** Only the control component grants execution; knowledge sources propose, the scheduler disposes. This is the problem baton's per-scope fences and single-writer scopes solve structurally: instead of scheduling proposals, admission-time authority decides who may write which layer at all ([context-networking.md](context-networking.md) §2.2).
- **Incremental state.** The blackboard holds partial solutions built incrementally, with each change visible to every knowledge source. This is the append-only cell store; the blackboard's "levels of analysis" map onto scopes and layers.
- **Control focus.** The control component maintains a focus of attention over the board's change events to pick the next contribution. The wake plane plus attention inbox (one attachment, ledger-seq cursor, mint-time coalescing) is a cursor-chained realization of the same need ([context-networking.md](context-networking.md) §2.2).
- **Direct ancestry.** The blackboard is the historical form of the primitive this program targets: independent contributors reading and writing one shared, incrementally-built state under an arbiter. The mapping rows in §5 transfer from it directly; the differences are that baton's contributors are processes holding their own contexts rather than in-memory knowledge sources, and the arbiter is an admission-time authority plus a wake stream rather than a run-time scheduler.

Why the pattern faded, as far as the sources record: the control problem is the architecture's center and its cost — an explicit scheduler must choose among eligible knowledge sources at every step, which made systems nondeterministic and expensive to tune, and the method's documented successes were interpretation problems (speech, signal) rather than open-ended construction. Nii's abstract frames the model/framework split and the control component's centrality as the open design surface ([AI Magazine 7(2)](https://ojs.aaai.org/aimagazine/index.php/aimagazine/article/view/537)). The recorded observation for this research program: no harness in the survey corpus ([context-networking.md](context-networking.md); [no-compaction-approaches.md](no-compaction-approaches.md)) implements blackboard-style opportunistic scheduling; every one replaces the scheduler with an explicit orchestrator (baton, NAC's DAG waves in [arcee-nac.md](arcee-nac.md) §2) or with the model's own calls (RLM subcalls, NOOA's Python fan-out). The blackboard's unresolved piece — what happens when two contributors write incompatible state — is precisely missing primitive 5, and the historical record is a warning that no scheduler solution aged well.

## 4. Plan 9 per-process namespaces

Plan 9 is built on two ideas: "every resource in the system ... is represented by a hierarchical file system; and a user or process assembles a private view of the system by constructing a file *name space* that connects these resources" ([Pike, Presotto, Thompson, Trickey, Winterbottom, "The Use of Name Spaces in Plan 9", 1992](https://9p.io/sys/doc/names.pdf)). The mechanisms:

- **9P.** A message-oriented file protocol (17 message types in the paper's description) where the auth/attach messages authenticate a connection and yield "an authenticated *channel* that points to the root of the server" — the channel, not the path, is the authority-bearing object, and every subsequent operation goes through it.
- **Per-process namespace assembly.** `mount` attaches a service's tree at a directory with replace/before/after flags (union directories searched in order); `bind` overlays an existing subtree; `rfork` shares or copies the namespace attribute, so child processes inherit or fork their view.
- **Synthetic per-client views of shared services.** The window system 8½ "is a server for files such as /dev/cons ... Each client sees a distinct copy of these files in its local name space" — one service, per-seat views, no kernel special cases.
- **No global namespace.** "Although there is no global name space, for a process to function sensibly the local name spaces must adhere to global conventions." Remote pieces enter via `import`, which dials a remote machine, starts a 9P server for a subtree, and mounts it locally; the `cpu` command recreates a terminal's namespace on a remote machine by importing the terminal's devices.
- **Version history as mounted subtrees.** The central file server creates a date-stamped copy of the root daily ("it creates a copy of the root directory and labels it with the current date, for example 1995/0314"), and old snapshots are browsable with ordinary commands through the same 9P interface.

Mapping onto per-seat synthetic views: each seat mounts exactly the slices of shared state it is granted — baton's layer policy (one `shared` layer plus one `worker:<id>` layer per fanout) is a fixed two-entry union, and a granted cross-session read is an `import`: a remote subtree attached into the seat's namespace under a grant, addressed through the seat's own citation grammar. The date-stamped dump is the passivation answer again: the snapshot exists as a mounted, immutable tree regardless of whether the producing session runs. The Plan 9 lesson against a deployment-scoped global namespace is direct: Plan 9 records that per-process assembly with global conventions beats a shared global tree, which supports the design question in §6 (question 2) toward run-scoped namespaces with grant-driven imports.

Three finer mappings. Union-directory ordering is layer precedence: Plan 9 searches a directory with several services mounted "in the specified order" (replace, before, after) — the semantics baton's layer policy gives the `shared` layer and the seat's own `worker:<id>` layer were both to define the same name; the REPL layer avoids the question by construction because layer namespaces are disjoint, and the Plan 9 record shows the alternative is a defined search order, not an error. The authenticated attach is the grant primitive: 9P's attach validates the user and yields a channel rooted at the granted subtree, so a narrower grant is a narrower attach root rather than a filter over a wider channel — the principle behind baton's "a subscription is a filter, never a second connection" applied to reads. The paper's backup example shows why the subtree boundary matters: the daily dump "still has protections; it is not possible to subvert security by looking at the backup," because the snapshot is served through the same per-channel authority as live data. Import is the cross-run mechanism: a remote subtree, served by a process on the remote machine, mounted into the local namespace under local control — the shape of a granted deref path into another run's binding history, with the remote run's orchestrator as the serving process.

## 5. Mapping onto the five primitives, with deltas as design questions

The rows below compress the mapping; three composition points deserve prose. First, the addressing half is already solved by content addressing: cell ids are global, hash-verifiable, and process-independent, so the remaining work is naming (row 1). Second, the authority half splits into two orthogonal prior-art contributions — cap systems supply derivation and revocation structure, macaroons supply request-time predicates — and a grant design can take both: a seL4-style derivation record for lifecycle and macaroon-style caveats for the per-deref check (row 2). Third, the consistency half has convergent evidence from four independent lineages — Datomic as-of reads, KeyKOS/EROS checkpoint persistence, Plan 9 date-stamped dumps, Cap'n Proto persistent capabilities — all pointing at the same rule: reads target durable values, never live processes, which is the "context of a session is its committed version line" definition proposed in [context-networking.md](context-networking.md) §3.3 (row 4).

## 6. Open questions

1. **Grant shape: per-deref vs per-scope lease.** seL4 mints are per-object and cheap in-kernel; a macaroon-style lease is one derived credential covering a scope with validity caveats. A per-deref grant makes every read an authorization event (auditable, revocable mid-task); a per-scope lease amortizes the round trip but widens the blast radius and re-raises the transfer question. Which shape the orchestrator's admission cost model favors is unmeasured.
2. **Namespace: run-scoped vs deployment-scoped.** baton's non-goal ("No cross-run bindings") plus Plan 9's recorded lesson (no global namespace; conventions plus per-process assembly) both point run-scoped, with knowledge-graph promotion as the deployment-scoped channel ([context-networking.md](context-networking.md) §3.3, §6). Whether any surveyed workload requires deployment-scoped citation remains unevidenced.
3. **Revocation semantics vs version pinning.** Revoking a grant and pinning a version are orthogonal (a Git tag outlives any ref authority); the design must state that revocation cuts future derefs, never retro-invalidates already-resolved citations, or stale-citation behavior stops being benign ([context-networking.md](context-networking.md) §5.2).
4. **Consistency across lanes.** Datomic's total order does not transfer to baton's per-scope fences; a cross-scope deref has no defined snapshot. Is one needed, or does every networked read name exactly one binding version?
5. **Non-transferability mechanism.** Channel-bound server-side enforcement (baton's current `claimGrant`) versus caveat-discharge (macaroons) versus badge pinning (seL4): which survives seat restart and re-admission, and does a discharge-based design require the seat to hold a durable identity the orchestrator already has (the manifest principal)?
6. **Unverified historical specifics.** The Hearsay-II mechanism description in §3 is corroborated from the paper's abstract-level record and secondary sources; the PDF body did not survive extraction. KeyKOS/EROS claims in §1.1 rest on the papers' standard summaries; neither PDF was read in full for this report.
