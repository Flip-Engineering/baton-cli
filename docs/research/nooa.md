# NOOA (NVIDIA Labs Object-Oriented Agents): the agent as a Python object, and compaction made unnecessary by reference

NOOA is NVIDIA's open-source agent framework built on one commitment: where Python already has the right abstraction, use it. An agent is a Python class whose methods are capabilities, fields are state, docstrings are prompts, and type annotations are runtime-enforced contracts; a method whose body is `...` is completed at runtime by an LLM-driven loop. This report is grounded in a code read of the repository shallow-cloned at HEAD `3187c6df9972dbffd33fc17317bfa337416c67fc` (2026-10-13, "Merge pull request #443", package `nooa`), with the technical report ([arXiv:2607.20709v1](https://arxiv.org/abs/2607.20709), 2026-07-22; the paper pins its own capability scoring at commit `59ae56bf`, 2026-07-01) and the [NVIDIA blog post](https://developer.nvidia.com/blog/six-agent-harness-capabilities-for-higher-model-performance/) (2026-07-27) as secondary sources. Claims cite repo-relative paths against the cloned HEAD; discrepancies between blog, paper, and code are registered in section 8. The report's focus is section 3: the no-compaction architecture, where tool results stay live as Python variables and the transcript records only bounded projections of them.

## 1. The object-oriented agent model

- The base class is `class Agent(metaclass=AgentMeta)` (`src/nooa/agent.py:74`). `AgentMeta` (`src/nooa/metaclass.py:25`) scans the class namespace at creation time and wraps async methods whose body ends in the ellipsis literal; `_should_generate` delegates to `has_ellipsis_body` (`src/nooa/ellipsis_detection.py:83`), which parses the source with `ast` after stripping the docstring. Everything else stays ordinary Python, wrapped only for tracing. Ellipsis-bodied generators are rejected outright (`_reject_ellipsis_generator`, `src/nooa/metaclass.py:216`).
- Strategies attach per method. `@strategy(...)` (`src/nooa/decorators.py:25`) marks the function with `_agent_decorator`; the metaclass skips already-decorated methods and resolves the strategy from the decorator (`_resolve_strategy`, `src/nooa/metaclass.py:190`). Undecorated ellipsis methods fall back to `get_default_strategy()`, which returns a fresh `CodeActStrategy(config=CodeActConfig())` (`src/nooa/strategies/__init__.py:45`). The decorator also carries per-method overrides for `llm`, `truncation`, and scoped `context`, so a classification method can run on a small model while the agent default serves open-ended work.
- The type contract is enforced at the return boundary. `CodeActStrategy.execute` raises `GenerationError` if the method has no return annotation (`src/nooa/strategies/codeact.py:900-904`), and `_handle_return_result` (`src/nooa/strategies/codeact.py:2127`) builds a one-field Pydantic wrapper model from the annotation, validates the submitted value, and on failure returns an error message to the model so the loop continues. The same handler resolves variable references: when the model calls `return_result` as a tool with a bare identifier, the harness looks the name up in the session namespace and substitutes the live object (`codeact.py:2225-2236`) — pass by reference crossing the tool-call boundary.
- Docstrings and parameter annotations are the prompt surface. `Annotated[T, "description"]` arguments render into the model-visible self-documentation; the `doc(self)` block is generated by `src/nooa/agentdoc/_pformat.py` as Python class syntax with field types and method signatures. Visibility is opt-out by annotation: `self.context` and `self.events` are declared `Annotated["ContextApi", hidden, nosnapshot]` (`src/nooa/agent.py:110-111`), so the harness APIs stay out of the model's self-documentation until a developer opts them in per instance (`spec(self, "context", hidden=False)`).
- Built-in strategies besides CodeAct: `PredictStrategy` (single-shot structured call with local validation retry, `src/nooa/strategies/predict.py`), `CodeActV2` (used by the benchmark agent, `src/nooa/strategies/codeact_v2.py`), `ReflexionStrategy`, `PurePythonStrategy`, `CompositeStrategy`, and a `Prefill` plugin protocol (`src/nooa/strategies/prefill.py`).
- Benchmark agents confirm the model in production. `packages/nooa-bench/src/nooa_bench/bench_agent.py` is 285 lines at HEAD (the paper says 253 at its pinned commit): `shell`/`repo`/`methodwriting` typed fields, one `_solve_task` CodeAct method returning a validated `TaskResult` (solution description, evidence, verification command), a depth-bounded `delegate` method (default max depth 4) that constructs a subagent of the same class, and a generic docstring with no benchmark-specific content.

Pattern: the class is the framework surface. Prompt engineering, tool schemas, validation, and orchestration reduce to ordinary Python declarations, so the same file is reviewable by humans and callable by models.

## 2. The six interface ideas, each with its code realization

1. **Typed input/output.** Agentic methods have annotated arguments (validated and injected as live objects) and an enforced return annotation; validation errors feed back into the loop rather than failing the call (section 1). Parameter descriptions come from `Annotated` metadata; per-field preview overrides use `spec(max_string=..., ...)` annotations.
2. **Pass by reference.** Two halves. On input: `InspectInputsPrefill.get_code` (`src/nooa/strategies/prefill.py:104-186`) generates a synthetic first cell that prints each parameter's type and a `pprint()` preview at `prefill_format` bounds, then prints the return type via `doc(_call.return_type, concise=True, inline_depth=1)`. On output: computed values return by reference from inside code (`return_result(variable)`), and tool-side variable-name references resolve from session locals (section 1). `PredictStrategy` is the deliberate counterexample: it serializes full argument values into the prompt under a hard `max_param_chars` cap that raises `ValueError` rather than truncating (`src/nooa/strategies/predict.py:397-434`), because a single-shot call has no opportunity to inspect variables.
3. **Code as action.** The CodeAct tool surface is two tools: `execute_python(code)` and `return_result(value)`. Cells run in a restricted Jupyter-like session with method arguments, `self`, and the agent module's imports preloaded as locals; restrictions reject `eval`, `exec`, `compile`, `__import__`, `input`, `breakpoint`, `globals`/`locals`/`vars`, `asyncio.run`, and attaching callables to the agent (`self.foo = fn`). Tracebacks render in IPython format with source locations. Cells can define `@strategy(PredictStrategy())`-decorated standalone functions and fan them out with `asyncio.gather` — the system prompt documents this pattern, and the paper's appendix B shows the model writing it.
4. **Programmable loop engineering.** Outer loops are ordinary Python methods; the inner loop is model-authored cells. The BenchAgent's `delegate` (`bench_agent.py:240-265`) is developer-written orchestration over a subagent of the same class; the model's fan-out over generated subcalls is model-written orchestration over the same callable primitives. No separate workflow language exists in either direction.
5. **Explicit object state.** Durable state lives on typed fields, rendered into a bounded dynamic block each turn. `PersistentVars` (`src/nooa/storage/persistent_vars.py:16`) documents the scoping contract: `self.v` for cross-task/cross-session identity and preferences, `todo.v` for per-task state, cell locals for transient scratch. Cross-session persistence goes through `AgentSnapshot` (section 3.4) — the boundary where live objects must become values.
6. **Model-callable harness APIs.** `ContextApi` (`src/nooa/runtime/context.py:25`) exposes `set_dynamic(key, expr)` and dict-style access over named blocks; `DynamicContext` validates the expression at creation time by compiling it (`src/nooa/context_blocks/models.py:25-55`). `EventsApi` (`src/nooa/runtime/events.py:21`) exposes `query(type=..., call_id=..., query=..., regex=...)`, tag access `events["5"]` and range summaries `events["1..22"]`, and `collapse(start_tag, end_tag, summary_text)` (`events.py:204-238`) — the model can compact its own history, and collapsed originals remain reachable through the summary's `children_tags`.

Pattern: one vocabulary for both audiences. Every capability the developer writes in Python, the model calls in Python, and the harness APIs the model can use are the same objects the developer configured.

## 3. The no-compaction architecture

### 3.1 What the transcript actually contains

Context splits into three regions rendered by two objects — `ContextManager` (static and dynamic blocks) and `EventManager` (typed events) — mapped onto LLM messages by a pluggable renderer (`src/nooa/context_blocks/`):

- **Static prefix** (cacheable, visible every turn): a ~1k-character framework system prompt, the strategy instructions (~2.5k characters for CodeAct), an execution-context block listing imported types and libraries, and the `doc(self)` self-documentation. Blocks marked static are retained under eviction; only non-static blocks are evictable (`src/nooa/context_blocks/renderer.py:112`).
- **Event history**: an append-only sequence of typed events (`Task`, `ToolCallEvent`, `PythonOutput`, `Error`, ...), each tagged `"1"`, `"2"`, ... and rendered as a typed Python repr. Events render in active-display order from `event_manager.values()` (`src/nooa/runtime/context_builder.py:447-452`).
- **Dynamic suffix**: a trailing user message re-evaluated before every model call. Dynamic blocks carry their expression in the rendered output — the paper's appendix B shows `<state expr="pformat(self, max_length=50, max_string=500, max_depth=4)">` — so the model sees that it is reading live state, not a frozen snapshot.

This layout is the cache argument: static prefix never changes, events only append, volatile dynamic blocks sit at the tail. Updates to live state re-render the tail without invalidating the cached prefix.

### 3.2 Preview bounding: the numbers

The bounds are data, not prose. `TruncationConfig` (`src/nooa/config/truncation_config.py`) defines five mechanisms, each with concrete defaults:

| Mechanism | Applies at | Default bounds |
| --- | --- | --- |
| `prefill_format` | parameter previews at method invocation (one-shot per call) | `max_string=2000`, `max_length=25`, `max_depth=4` |
| `event_format` | event-field rendering every turn (incl. `PythonOutput.value`) | `max_string=10_000`, `max_length=200`, `max_depth=5` |
| `capture` | raw stdout/stderr/error per `execute_python` cell | stdout 50,000 chars; stderr 2,000; error 10,000; head/tail split |
| `media_capture` | attachments captured by `show()` | 5 per cell |
| `context_block_format` | author-curated blocks via `self.context[key]=value` | unlimited; whole-block eviction at assembly |

The prefill defaults reproduce the paper's traced inspection cell exactly: `pprint(texts, max_length=25, max_string=2000, max_depth=4)` (paper appendix B, `prefill.py:145-152` wiring `prefill_format` into the generated code). Per-parameter overrides come from `Annotated[T, spec(...)]` metadata (`prefill.py:165-172`); the BenchAgent uses one to uncap a task description entirely (`_TaskDescription = Annotated[str, spec(max_string=None)]`, `bench_agent.py:42`).

The preview format is the contract the model learns: `list(len=100, [:5]=[42, 17, 89, 33, 8], [-5:]=[56, 71, 12, 45, 28])` for containers, `str(len=100000, [:250]='...', [-250:]='...')` for strings, `Config(name='foo', enabled=True, ...)` for structured instances. The system prompt states the invariant directly: "The variable itself is **not** truncated --- index/iterate it directly to operate on the full data," and warns that `<truncated>...</truncated>` markers in captured stdout are **not recoverable** (paper appendix B). `pformat` was borrowed from Rich's name and API surface — both are in model training data — with a custom output format chosen by experiment (paper §3.2; implementation in `src/nooa/agentdoc/_pformat.py`).

### 3.3 What stays live and what the transcript never sees

The execution environment is the second data plane. A `CodeActSession` holds `session_locals` — a dict that persists across cells within one agentic call and is written back to the caller's dict at completion with internal keys filtered (`_sync_session_locals`, `src/nooa/strategies/codeact.py:822-832`). Method arguments bind as locals in that dict; a method receiving a multi-million-row table carries the full object in the session while the transcript carries one bounded preview. The paper's claim is exact: "the amount of data an agent can process is bounded by the execution environment, not by the prompt."

Scoping follows Python rules, which is what makes the no-compaction design safe: locals are method-scoped and die when the method returns (paper §3.5), so intermediate values do not accumulate across the session; anything reached through `self` or module-level objects can outlive the call, and anything that must survive the process goes through the persistence layer below.

### 3.4 Where serialization does happen

The architecture serializes at exactly one boundary: durability. `AgentSnapshot` (version 2, `src/nooa/storage/snapshot.py:40`) captures context blocks and attributes as a JSON-compatible structure; `serialize()` (`src/nooa/storage/serialization.py:72`) handles primitives, enums, and four envelope types (`pydantic`, `dataclass`, `dict_class`, `tuple`), recording class fully-qualified names in a type allowlist that `deserialize()` re-imports at restore time. Fields marked `nosnapshot` are skipped (`src/nooa/storage/markers.py`). `PersistentVars` states the rule for values that opt into durability: "Values must be snapshot-serializable ... unsupported live objects are not stored" (`persistent_vars.py:36-37`). Events persist separately: the default backend is `InMemoryBackend`, and `SQLiteEventBackend` (`src/nooa/runtime/event_backend.py:225`) writes the typed event log to one SQLite file with schema migration, corruption detection, and file-lock handling.

So the lifecycle is: live by reference within a process and session; by value at the session boundary (snapshots, `self.v`, `todo.v`, memory records, files); never serialized through the model context unless the author chooses to place a value in a context block.

### 3.5 The economics and the cache argument

On SWE-bench Verified with GPT-5.5 at xhigh effort, the paper reports NOOA at 82.2% using approximately 28 model calls and ~1.1M tokens per task, against OpenCode at 78.6% with a similar call count and ~1.3M tokens, and PI at 78.2% using 66 calls and 2.2M tokens (paper §4.2; the blog rounds to 29 calls). The mechanism is the two data planes: tool outputs stay live as values, so they are never round-tripped through the transcript; the transcript grows only by bounded previews, errors, and the model's own code and text.

The cache claim follows from the layout. Because the static prefix is byte-stable and events append-only, each turn reuses the previous prefix computation. The repo's `docs/cache-sharing-summaries.md` documents the design constraint that even the optional summarizer must preserve: the summary fork reuses the parent request's actual rendered prefix (copying only dict/list containers, sharing immutable objects) so the summary request itself hits the provider cache, and "the prompt prefix is append-only."

### 3.6 The boundaries: compaction exists, it is just not needed

This is the report's central correction to the blog framing. NOOA does not lack compaction machinery; it ships three compaction paths, and the design keeps them dormant by keeping transcripts far below thresholds:

1. **Opt-in proactive summarizer.** `TokenBudgetSummarizer` (`src/nooa/agents/summarization.py`) replaces older conversation messages with a model-written summary. `SummarizationConfig` defaults to `policy="token_budget"` triggering at 75% of the usable input window with `preserve_recent=10` and 4,000-character summaries (`src/nooa/interactive.py:216-228`). The shipped benchmark agent **installs it by default** (`install_summarizer(self._summarization, self)`, `bench_agent.py:157,167`). At the paper's reported peaks, the threshold is never crossed; the summarizer is a safety mechanism at 75% of the window, not a routine pass. The blog's "doesn't need context compaction" is accurate as a statement about triggering, not about capability.
2. **Reactive overflow archive.** `_archive_on_context_error` (`src/nooa/runtime/actor.py:663`) fires only when the provider actually rejects a request as too large. It sheds the oldest events toward 70% utilization of the usable window, using the provider-reported token count when available and a calibrated chars-to-tokens estimate otherwise. Failed summaries leave history unchanged; raw archived events remain in session storage (`cache-sharing-summaries.md:43-45`).
3. **Model-callable collapse.** `self.events.collapse("2", "40", summary)` replaces a range with one `Summary` event tagged `"2..40"`; originals stay addressable by tag and searchable via `events.query()` (`src/nooa/runtime/events.py:204-238`; `src/nooa/runtime/event_manager.py:639`). The event manager's docstring records the design: string tags give stable access even after summarization.

Separately, `max_context_tokens` (default: half the usable window, `(context_window - reserve) // 2`, `src/nooa/runtime/actor.py:3005-3013`) budgets the **context blocks** — over-budget blocks are marked `EVICTED: over context budget (block_tokens=N)` in place (`renderer.py:85-134`). Events are never individually evicted by budget: the config fields `max_event_tokens` and `min_preserved_events` are retained as visible no-ops pending a context-API refactor (`truncation_config.py:29-34,191-208`). Token accounting needs no tokenizer: counts are chars multiplied by a provider-calibrated ratio (prompt tokens over total characters from the last response), corrected per model by an EMA tracker (`tests/test_token_calibration.py`; `src/nooa/unifiedllm/unifiedllm.py` `TokenCalibration`).

Failure modes and limits, as implemented:

- Unrecoverable truncation exists in one place: head/tail-captured stdout past 50,000 characters is elided with `<truncated>...</truncated>`, and the system prompt tells the model this is not recoverable. A `file_backed` capture option streams the full output to a temp file and puts the path in the notice (`truncation_config.py:70-80`) — the escape hatch, and one of the few places a harness-supported artifact crosses into the filesystem.
- Very long tasks grow the event log without per-event budgeting; the only releases are the three compaction paths above. A session doing many large-but-bounded outputs (10,000-character event fields) accumulates linearly.
- Cross-session restart loses REPL locals by design (method-scoped). Work that must survive goes through typed fields, `self.v`/`todo.v`, memory, or files — all by value.
- In-process execution is the default (`execution_backend: Literal["inprocess", "sandbox"] = "inprocess"`, `src/nooa/config/strategy_config.py:113`) and is what preserves pass by reference; the opt-in sandbox backend runs cells in a locked-down worker process, and the paper's limitation section is explicit that sandboxed code modes trade reference semantics away at the boundary.

Pattern: budget the projection, not the value. Every other surveyed harness budgets tool results as text; NOOA budgets only the previews it must render, keeps values in the process, and reserves serialization for the durability boundary — which leaves compaction as an unused safety net rather than a load-bearing stage.

## 4. The memory subsystem

`packages/nooa-memory` implements the paper's §3.7 as an attachable component: `MemoryManager.install(agent)` mutates nothing on the agent class, and `uninstall()` restores it exactly (`src/nooa_memory/manager.py:187,230`).

- **Agent-curated writes.** Seven model-callable tools via `MemoryToolsMixin`: `remember`, `recall`, `search`, `update_memory`, `forget`, `associate`, `deref` (`manager.py:799+`). Importance accepts ordered verbal descriptors mapped to numeric scores internally.
- **Typed records and graph.** `MemoryType` covers `info`, `skill`, `episode`, `todo`, `reflection`, `scratch`; `EdgeType` defines directed typed edges — `supports`, `contradicts`, `derived_from`, `causes`, `refines`, `created_by`, `triggers`, `related` (`src/nooa_memory/schema.py:27-58`). Records carry importance, tags, confidence, and a bounded access log (64 entries).
- **Live references.** `MemoryRef` is a typed pointer into live agent state with kinds `("var", "context", "file", "todo", "memory")` (`schema.py:129-153`), resolved at recall time by `deref` (`manager.py:488`) — the paper calls this "extending pass by reference into persistence," so recall answers from current state rather than stale copies.
- **Two read channels.** Deliberate: the model's own tool calls. Spontaneous: a `BeforeTurn` hook derives a query from recent events and injects matched memories into a dynamic context block (`manager.py:671,599`). Injection is logged but deliberately excluded from the channels that reinforce ACT-R activation (`schema.py:75-82`), so harness-driven surfacing cannot inflate a record's retrieval priority.
- **Ranking and forgetting.** Retrieval unions embedding and keyword candidates, ranks by ACT-R activation (relevance, recency, importance — the generative-agents triad), and propagates activation over the typed graph; decay-based forgetting bounds the store (`src/nooa_memory/retrieval.py`, `forgetting.py`).
- **Reflection.** An asynchronous consolidation pass merges near-duplicates, reconciles conflicting values (archiving superseded records), links related records, re-scores importance, distills episodes, and prunes decayed memories — never removing recent memories, protected types, or open todos (paper §3.7; `src/nooa_memory/reflection.py`).
- **Storage.** One human-inspectable SQLite file (`src/nooa_memory/store.py`, `MemoryStore` over `sqlite3`, embeddings as blobs); vector indexes are derived and pluggable (`vector_backends.py`). Owner scoping (`role[@instance]`) governs multi-agent sharing of one store.

Measured effect (ARC-AGI-3 fleet, paper §4.4): +11.8 RHAE over the same agent with markdown-file notes (50.2% vs 38.4%), 3,262 memories written, 12,654 spontaneous injections, 27,115 deliberate recalls at a 99% hit rate, injection bounded at 4.1 memories per turn, and recalls per decision correlating with levels completed (Spearman ρ = +0.52).

## 5. Benchmark results with linked evidence

- **Capability tests** (paper §4.1): 88 test families × 5 runs × 10 models = 4,400 records, 97.9% overall; frontier models 99.2%; GPT-5.5 440/440. The suite ships in the repo (`tests/`).
- **SWE-bench Verified** (paper Table 3): NOOA 67.2 / 78.8 / 82.2 (GPT-5.5 off/high/xhigh) and 76.8 / 79.8 (Opus 4.6 off/high); OpenCode 1.14.33 at 59.2 / 75.0 / 78.6 and 76.0 / 75.2; PI 0.72.1 at 60.8 / 73.6 / 78.2 and 75.6 / 75.8. Published leaderboard SOTA at submission: 79.2%. Same benchmark-agnostic agent, no benchmark-specific prompts (verified: `bench_agent.py` docstring is generic).
- **Terminal-Bench 2.0** (Table 4): NOOA 46.1 / 73.0 / 73.0; OpenCode 34.8 / 60.7 / 52.8; PI 37.1 / 68.5 / 75.3 (PI best at xhigh); Opus 4.6: NOOA 65.2 vs 43.8 / 58.4. Trace analysis: 77% of OpenCode's failed GPT-5.5 trials terminate within ten steps, against NOOA's validated-`TaskResult` termination (root cause, evidence, verification command) — type-annotated termination as an executable contract.
- **CyberGym L1** (Table 5): NOOA 86.8% with GPT-5.5, network blocked, rule-based cheat check over trajectories — top open-source result, ahead of OpenAI Codex (64.9% blocked) and most closed systems; the repo ships the agent (`examples/cybergym/nooa_cybergym/agent.py` — `Finder`, `Expander`, `CyberGymAgent` classes with a deterministic `submit` gate that reruns proofs to reject non-deterministic crashes).
- **ARC-AGI-3** (paper §4.4): 50.2% mean RHAE on GPT-5.5 at $17.85/game and 85.1% on GPT-5.6-sol at $13.28/game, both under the two-hour cap and $20/game ([GPT-5.5 scorecard](https://arcprize.org/scorecards/b2aa2240-8cd7-41cf-ad83-edf8c2836084), [GPT-5.6-sol scorecard](https://arcprize.org/scorecards/7a511ea0-dfa1-47ed-8a99-52a80f3cdbaa)); the blog reports 19 of 25 games fully solved by the GPT-5.6-sol fleet. Against ARC Prize's own 13.3% evaluation of raw GPT-5.6-sol, the harness effect is 6.4x. The world-model skill (`examples/arc_agi_3/skills/interactive-game-solver/SKILL.md`, 51 lines at HEAD) instructs the agent to persist `encode(grid) -> z` and `predict(z, action) -> z'` as Python modules, retrodict every turn against observed state, search over its own predictor, and record hypotheses to memory; the solver agent (`examples/arc_agi_3/solver_agent.py`, 1,174 lines) runs the game over append-only JSONL file IPC. Containment: per-cell Landlock deny-by-default, seccomp network block, per-run privilege drop, opaque game aliases; an 18-pass red-team audit over 13,335 logs found no leakage.

## 6. Comparison with the sibling reports' context-management approaches

Against [fx](fx.md): fx budgets tool results as bytes at the boundary — 64 KiB model-visible cap, spill to a content-addressed session store above 16 KiB with a 4 KiB preview, `read_tool_result` paging — and compacts by lossy-verbatim reclamation that keeps user intent and final answers verbatim while displacing everything else into searchable records. NOOA has no byte budget on values at all; its bounds apply to projections (previews and event fields), and its "store" is the Python process itself. Both designs decouple model-visible bytes from captured bytes, but fx displaces by value into files and re-materializes on demand, while NOOA never displaces within a session — the displacement boundary is process lifetime, not context pressure.

Against [dsh](deepseek-harness.md): the session shapes converge. dsh's invariant "model-visible means logged" over an append-only `SessionEvent` log matches NOOA's typed, tagged event log rendered as model-visible messages, and dsh's PTC (model calls tools as functions inside an executing program, keeping bulk intermediates out of context) is the same move as CodeAct. The difference is the second data plane: dsh's programmatic tools return values into the calling program's scope within one turn, while NOOA's session locals persist across every cell of a method call and its typed fields persist across the session — statefulness across turns, not just within one.

Against [pi](pi.md): pi compacts at turn boundaries with cut-point validation (`isCutPointMessage` rejects `toolResult`, so a result can never be separated from its call, `compaction.ts:351`), carries a full system checkpoint in each `CompactionEntry`, and truncates tool results to 2,000 chars in the summary call. NOOA sidesteps the cut-point problem: its only archival collapses whole event ranges after the fact (on API error or model call), the collapse never splits a call from its output because it operates on contiguous ranges, and originals remain addressable by tag — a weaker guarantee than pi's structural cut points, bought by needing the mechanism far less often.

Against [prime-agent](prime-agent.md): the closest cousin. Prime makes the model's context a variable in a persistent CPython kernel with bounded result ingress (1 MiB kernel-side, 64 KiB host-side) and per-variable durable snapshots (256 MiB ceiling; unpicklable values skipped and reported). NOOA reaches the same shape without a separate kernel: the agent object itself is the execution environment, in-process by default. The contrasts are instructive. Prime persists per-variable best-effort and compacts by removing oversized variables; NOOA persists only snapshot-serializable typed fields and refuses live objects at the durability boundary outright. Prime's 64 KiB output cap sits on every execution; NOOA's 50,000-character cap sits on captured stdout per cell while return values cross unbounded. Prime's kernel is a subprocess with a versioned wire protocol; NOOA's is the host process, which is precisely what its sandbox story (opt-in, per-cell, OpenShell for deployment) has to compensate for.

The distinctive NOOA position across all four: every sibling treats tool results as text that must be budgeted, spilled, cut, or removed. NOOA treats them as values to be referenced, and spends its engineering on making the projections the model does see small, typed, and cache-stable.

## 7. Open questions and uncertainties

- The blog's quantitative anchor — "median sessions peak at 22–72k prompt tokens against 200–400k windows" — appears nowhere in the paper text; the paper states only that bounded previews keep NOOA "well below the context limit." The figure is plausible given the architecture but unverifiable from the primary sources read for this report.
- Call-count rounding: blog says 29 LLM calls per SWE-bench task; paper says "approximately 28 calls." Token figures (~1.1M) agree.
- The 253-line BenchAgent claim matches the paper's pinned commit; at this clone's HEAD the file is 285 lines (`packages/nooa-bench/src/nooa_bench/bench_agent.py`). The ARC-AGI-3 skill is 51 lines at HEAD against the blog's 45 and the paper's "50-line."
- Whether the paper's SWE-bench runs had the summarizer installed is not stated; the shipped BenchAgent installs it by default at HEAD, and the reported token peaks imply it never triggered — but the exact run configuration is not in the paper.
- Per-event budget enforcement is explicitly unfinished: `max_event_tokens` and `min_preserved_events` are documented as visible no-ops pending a context-API refactor (`truncation_config.py:29-34`). Long-session behavior therefore rests on the overflow archive and the summarizer.
- Coverage of `nosnapshot` over third-party live objects (DataFrames, database handles) is declared rather than demonstrated in the code read; the serialization layer handles four envelope types and skips marked fields, but which agent-authored types opt out in practice is not documented.
- `CodeActV2` (the strategy the shipped BenchAgent uses) is 11.5 KB against `codeact.py`'s 147 KB; the deltas between the two were not analyzed for this report and may matter for anyone reproducing the benchmark numbers.
- The paper's 6.4x ARC-AGI-3 harness effect compares against ARC Prize's own evaluation "at maximum reasoning effort" with differing budgets; the paper itself marks the comparison as indicative.

## 8. Corrections register (blog and paper vs code)

- "NOOA doesn't need context compaction" (blog) is a statement about triggering, not absence: the framework ships an opt-in proactive summarizer (installed by default in the benchmark agent), a reactive overflow archive, and a model-callable collapse API. Nothing in the code prevents compaction; the architecture makes it unnecessary at reported token levels.
- The blog's "22–72k median prompt tokens" figure is blog-only (see section 7).
- "45-line world-modeling skill" (blog) vs 51 lines measured at HEAD (`examples/arc_agi_3/skills/interactive-game-solver/SKILL.md`); the paper says "50-line."
- The blog's memory claim "typed relationships like supports/contradicts/derived-from" is verified and broader in code: `EdgeType` also defines `causes`, `refines`, `created_by`, `triggers`, `related` (`src/nooa_memory/schema.py:39-51`).
- The paper's "253-line agent" is commit-pinned; 285 lines at this clone's HEAD.
- The paper's §3.2 example shows a preview of "ten elements" for a 100-element list; the shipped default prefill bound is 25 elements (`max_length=25`), and the paper's own appendix trace uses 25. The ten-element figure matches the paper's inline example, not the shipped default.
