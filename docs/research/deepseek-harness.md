# DeepSeek Harness (`dsh`) — Deep Dive

DeepSeek Harness (`dsh`) is DeepSeek AI's open-source agent harness: a TypeScript monorepo distributed as the npm package `@deepseek-ai/dsh`, licensed MIT, built on the vendored Cordis plugin framework ([README](https://github.com/deepseek-ai/deepseek-harness); [rescope doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/rescope.md)). Every part of the product — the model adapter, tool registry, session log, and the agent loop itself — is a plugin mounted into a composed plugin tree, so each is replaceable from configuration files with no privileged core ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)). The harness ships named surfaces (`web`, `headless`, `sdk`, `sdk-minimal`, `acp`) and, for the web surface, named agent presets that change the toolset, system prompt, and tool-call wire protocol: `standard`, `ptc`, `minimal`, and `cordis` (creator mode) ([web-app README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/README.md)). Its most distinctive mechanism is PTC (programmatic tool calling): the model writes a short TypeScript program against a generated SDK instead of emitting one tool call per turn, and the program calls host bindings that re-enter the full guarded tool pipeline ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md)). Sessions are append-only, event-sourced logs persisted as versioned JSONL with defined crash-recovery, fork, and resume semantics ([persistence doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)). For baton-cli, the directly reusable ideas are the preset/patch composition model, the PTC batching contract, and the event-log-plus-turn-enclosure session format; the Cordis microkernel machinery and the very large plugin surface are not.

This report was upgraded from doc-level research to code-level analysis of the repository cloned at commit `571902028a75c64c1d767f4ae5fd099485f0ddf0` (shallow clone of `master`, 2026-10-14). Subsections marked "code-level" cite repo-relative file paths against that commit. Where the code and the docs pages differ in emphasis or detail, the code reading stands; one docs-page under-description was found and is corrected in section 4.1.

## 1. The model-plus-harness split as implemented

The repo frames itself as "everything is a plugin" and links a Cordis design paper ([README](https://github.com/deepseek-ai/deepseek-harness); [Cordis paper, arXiv:2608.25512](https://arxiv.org/abs/2608.25512)). The community framing "separates model weights from harness scaffolding" is accurate at the product level — DeepSeek ships models through its API and the harness is a separate codebase — but the repo itself states the architectural claim differently: model access is a plugin seam, and the shipped model adapter package is `@deepseek-ai/dsh-llm-deepseek` alongside `dsh-llm-pi-ai` (the pi-ai adapter package, reused from the Pi project's adapter layer) with providers for `anthropic`, `openai`, `moonshotai` (Kimi), and `zai` (GLM), plus custom OpenAI Chat Completions / OpenAI Responses / Anthropic Messages gateways ([providers guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/providers.md); [config catalog reference to dsh-llm-pi-ai](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md)). The web default route is `deepseek-official` / `deepseek-flash` (DeepSeek-V4.1-Flash) ([web-app README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/README.md)). A session that has already sent a request retains the model recorded in its own log ([providers guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/providers.md)).

What lives in the harness, concretely ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md); [core subsystem doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md)):

| Package | Owns |
|---|---|
| `core/session` | Append-only `SessionEvent` log and in-memory store |
| `core/system-prompt` | Prompt-section and tool-schema assembly |
| `core/tools` | Scoped tool registry and guarded execution pipeline |
| `core/agent` | `Agent` interface, live registry, `agent/*` events |
| `core/agent-loop` | The default driver implementing the `Agent` interface |
| `core/scope` | Per-agent scoped-registration primitive |
| `llm/llm` | Message/stream vocabulary and the adapter seam |

The loop is swappable: extension plugins depend on the `Agent` interface package and never on `agent-loop` directly ([core doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md)). Everything the model sees is derived from the session log: "model-visible means logged"; every model request must be reconstructable from the log ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)).

### 1.1 The agent loop as code

The shipped driver (`packages/core/agent-loop/src/agent.ts`) is a three-phase state machine — `idle`, `maintenance`, `running` — wrapped around one `turn()` loop (`packages/core/agent-loop/src/agent.ts:298-398`). The code makes the invariants mechanical rather than documented:

- `turn/start` is appended before the first pre-step claim, and `turn/end` is appended in a `finally` block that requires every exit path to have assigned a reason (`completed`, `blocked`, `aborted`, `error`, `max-tokens`) (`packages/core/agent-loop/src/agent.ts:298-391`).
- Input admission is a `agent/pre-step` waterfall over a claimed inbox batch; a rejected or emptied first claim closes the turn without a model call (`packages/core/agent-loop/src/agent.ts:267-288`). Steering and injected context land in the `next-step` inbox, follow-ups in `next-turn` (`packages/core/agent-loop/src/agent.ts:154-173`).
- Failed steps are healed in the log, not in memory: a `ToolCallRecovery` observer tracks pending tool calls during the step, and if the step throws, it appends the missing `tool/result` events (linked by `sourceEventSeqs`) before the error propagates, so the log never ends with an unanswered tool call (`packages/core/agent-loop/src/agent.ts:333-359`; `packages/core/session/src/repair.ts:100-198`).
- An assistant stream aborted mid-flight settles as an `assistant/message` marked `interrupted: true` when it produced content, otherwise as a log-only `assistant/attempt`; retries and stream errors always leave a durable settlement (`packages/core/agent-loop/src/agent.ts:462-503`).
- Each request is derived and deep-frozen from the log (`session.deriveMessages()`, cached per message identity in a WeakSet), and header changes log `request/header` events whose `tool-addition`/`tool-removal` deltas also emit `developer/message` events (`packages/core/agent-loop/src/agent.ts:616-704`).
- The per-step tool scheduler (`packages/core/agent-loop/src/tool-calls.ts:122-247`) is a rolling pool: consecutive parallel-classified calls overlap up to `DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10` (`packages/core/agent-loop/src/constants.ts`), results commit in model order through a head-of-line cursor, an exclusive call drains the pool and holds its barrier through post-execute, classification is re-read immediately before each start, and abort appends synthetic results for every skipped call. `max-tokens` is sticky for the whole turn: a later normally-completed step cannot downgrade the outcome (`packages/core/agent-loop/src/agent.ts:338-343`).
- Even pending input is durable: the inbox is a projection over `agent/inbox/spliced` events that validates and rejects malformed durable splice history (`packages/core/agent-loop/src/inbox.ts`).

## 2. Plugin architecture: Cordis, profiles, bundles, patches

Cordis is a Context/Service/event framework vendored from `cordiverse/cordis` and republished under `@deepseek-ai/cordis` (4.0.0-rc.7 snapshot), with `plugin-loader`, `plugin-include`, `plugin-group`, `plugin-timer`, and `plugin-hmr` also vendored ([rescope doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/rescope.md)). Plugins contribute services, typed events, and reversible effects to a shared context; unloading a plugin unwinds its registrations ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)).

Composition is layered YAML:

- A **profile** is a named composition in `$DSH_HOME/profiles/<name>` holding an ordered bundle list and the user's `cordis.patch.yml`.
- A **bundle** is a patch layer distributed as an npm package declaring `dsh.bundle.patch` in its `package.json`.
- Layers stack: the profile's ordered bundles, then the profile patch, then the home patch, then `--patch` overlays. A patch replaces a row's whole config by id or inserts rows ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md); [CLI README](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md)).

`dsh-base` is the shared first layer of the full profiles: model adapters, tools, persistence, sandbox and approval policy, settings, credentials, telemetry. `dsh-sdk-minimal` is the deliberate exception — one bundle owns its complete standalone tree and skips `dsh-base` ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)). A plugin manager tool lets the model list/install bundles; installation requires danger-full-access permission or per-call approval ([tool catalog](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md)).

### 2.1 Capability seams: the swap points

A **seam** is a swappable capability with three roles: a Service Definition (abstract class owning a `ctx.<key>`), Service Providers, and Consumers ([glossary](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/glossary.md)). The canonical example: `dsh-shell` (definition), `dsh-bash-local`/`dsh-bash-sandbox` (providers), `dsh-tool-bash` (consumer) ([glossary](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/glossary.md)). The documented swap points relevant to baton-cli:

- **Session persistence** — abstract `SessionPersistence` (`ctx.sessionPersistence`) with `create`/`open`/`stat`/`list`/`export`; the repo ships a JSONL provider, and out-of-tree providers may implement the same contract. SQLite appears as a full-text query index provider (`dsh-session-query-sqlite`) layered over the logical corpus, not as the primary log format ([persistence doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md); [session-query doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session-query.md)).
- **Execution world** — `ctx.fs` and `ctx.subprocess` describe one shared path namespace and process world; filesystem and shell providers share it, so repointing both at a remote host moves Bash, PTY, and LSP together with no provider forks ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)).
- **Sandboxes** — `ctx.sandbox` wraps a subprocess argv in a file-effect policy; `dsh-sandbox-local` supplies Linux bwrap/Landlock, macOS Seatbelt, and Windows ACL backends; `dsh-sandbox-ssh` applies the same policy through remote providers ([sandbox doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/sandbox.md)).
- **Shells** — `ctx.shell` backends plus one-shot (`dsh-tool-bash`, `dsh-tool-pwsh`) and persistent PTY (`dsh-tool-bash-persistent`, via `ctx.terminals`) consumers ([tool catalog](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md)).
- **Subagents** — `ctx.subagents` manages local children (durable sessions, continuable, follow-up-able) and external executions (single-shot) behind one activation API; the shipped local presets configure `provider: spawn` (fresh child) and `provider: fork` (child seeded with parent history), and an SDK provider can run the child in a separate dsh runtime ([subagent doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md); [PTC preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/ptc.patch.yml)).
- **PTC execution** — `ctx.ptcRuntime` is language- and substrate-agnostic: TypeScript on Node is shipped, Python is experimental, and a container backend would be another provider package ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md); [PTC runtime doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/ptc-runtime.md)).
- **LLM adapters** — register on `ctx.llm` ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)).

One verified counterexample matters for expectations-setting: dsh previously shipped E2B remote-sandbox providers and removed them on 2026-09-11. The stated reason: PTC Node confinement needs a bidirectional control channel separate from program stdin/stdout, the pinned E2B SDK retained complete stdout/stderr even under backpressure (unbounded host memory), and extending the adapter would have become a separate remote-transport project. Remote execution remains intended; SSH providers now use binary channels outside the E2B command SDK's retained-output path ([E2B removal note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/simplification/2026-09-11-remove-e2b-providers.md)).

## 3. Runtime modes (agent presets)

The web surface composes per-session agent presets, each a `@deepseek-ai/dsh-agent-preset` plugin declaration inserted by its own patch file; the browser session picker selects one, `standard` by default, and edits persist in the profile patch ([web-app README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/README.md)). Shipped presets: `standard` (order 1), `ptc` (order 2), `minimal` (order 3), and a `cordis` creator preset with read-only runtime-inspection tools ([presets directory](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/); [tool catalog note on creator mode](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md)). A preset is a plugin list plus optional `isolate` realms (e.g., an isolated compaction backend per preset). A related but distinct notion is the standalone `sdk-minimal` profile — a whole-profile tree with three tools and danger-full-access ([sdk-minimal README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/sdk-minimal/README.md)).

### 3.1 `standard`

A full coding agent: persona prefix "You are a coding agent powered by the {{model}} model.", user instructions (max 65,536 bytes), time context, and these model-facing tools/plugins: one-shot `bash` (non-Windows) or `pwsh` (Windows), `read`/`write`/`edit`/`read_image` (`tool-fs`), `glob`/`grep` (`tool-fs-search`), background-job controls (`tool-jobs`), schedule management, skills (`tool-skill` + filesystem skills), goals (`tool-goal` + `/goal` command), plan mode (`plan-mode` with `exit_plan_mode`), compaction group (basic compaction, `/compact`, tool-result pruning at 8,192 chars with 4,096 head / 1,024 tail), delegation group (`subagent` spawn, `subagent_fork`, `send_message`/`interrupt_agent`/`list_agents`, workflow tools), `ask_user_question`, `todo_write`, `web_search`/`web_fetch` (fetch enabled, 60 s search timeout), and `present` (deliverables). Plugin-manager tools are present but disabled ([standard preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/standard.patch.yml)).

Notable design choice stated in the plan-mode prompt: "The tool catalog stays the same across modes for request-cache stability" — mutating tools remain listed in plan mode with rules overriding their descriptions, so the schema block never changes ([standard preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/standard.patch.yml)).

### 3.2 `ptc`

Identical to `standard` except two changes: it adds `@deepseek-ai/dsh-agent-tool-presentation` with `mode: ptc`, which switches the tool registry's wire presentation to PTC (see section 4), and it disables the `workflow` tool and the PTC workflow variant. The tool-list change is visible in the preset diff: `workflow-ptc` and `tool-workflow` rows are `disabled: true`, and the presentation row is added ([PTC preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/ptc.patch.yml)).

### 3.3 `minimal`

The `minimal` preset is the smallest shipped interactive composition. Its plugin list ([minimal preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/minimal.patch.yml)):

- A fixed persona: "You are a helpful software engineer assistant.", with `includeRuntimeContext: false` — no runtime-context snapshot section.
- No text file tools: `tool-fs` is mounted with `read: false, write: false, edit: false, readImage: true`. The only file tool is `read_image`.
- A persistent-shell group in an isolated `terminals` realm: `dsh-terminal` PTY backend plus platform-selected `dsh-tool-bash-persistent` (Linux/macOS) or `dsh-tool-pwsh-persistent` (Windows), 300-second timeouts, with a fixed bash description ("Run commands in a bash shell … State is persistent across command calls and discussions with the user. … avoid commands that may produce a very large amount of output … run long lived commands in the background").
- An isolated compaction group: `compaction-basic` plus the `/compact` human command.

What changes versus `standard`: the tool roster collapses from roughly two dozen schemas to a persistent shell plus `read_image`; there is no plan mode, no subagents, no todo/web/goal/presentation/ask-user tools; there is no runtime-context block. File reading, writing, and searching all flow through shell commands. The web README describes the same preset in prose: persistent shell, `read_image`, fixed persona, automatic history compaction and idle-session `/compact` ([web-app README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/README.md)). The standalone `sdk-minimal` profile goes one step further: exactly `read_image`, `working_directory`, and one persistent shell; uncompressed JSONL; `DSH_SYSTEM_PROMPT` replaces the persona; danger-full-access policy with the explicit instruction to use an isolated workspace ([sdk-minimal README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/sdk-minimal/README.md)).

## 4. PTC mode in detail

PTC is grounded in the observation (credited to Cloudflare's Code Mode) that LLMs write code better than they emit contrived tool-call traces, and that only what a program prints or returns should re-enter context — every intermediate tool result stays out ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md); [Cloudflare Code Mode](https://blog.cloudflare.com/code-mode/)).

Mechanics ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md)):

- The registry's `mode` config is `'native' | 'ptc'`, default `'native'`, set from YAML (`tools: { mode: ptc }`); mixed presentation was later removed ([presentation simplification note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/simplification/2026-10-05-native-or-ptc-presentation.md)).
- Under `'ptc'` the registry contributes exactly one reserved wire tool, `run_code`, with required parameters `{ code, description }` (the description labels the call in the UI), plus a generated SDK section (`tools:sdk`) in the system prompt: TypeScript `.d.ts`-style declarations for every visible capability, sorted lexicographically for byte-stable caching, excluding `run_code`. A configured `toolOrder` naming native capability names makes every PTC assembly fail — stated as correct behavior.
- The model writes an async body: `await tools.name(args)` per call, `Promise.all` for independent read-only calls, `await` sequencing otherwise; the SDK text states this concurrency contract explicitly. Programs are erasable-TypeScript (no enums/namespaces/parameter properties); type errors are caught only because the runtime strips types before execution, so typing is advisory. Python support exists under an experimental provider with `asyncio.gather` as the parallel primitive ([language-dispatch note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/archived/feature/2026-07-31-ptc-language-dispatch.md), referenced from the PTC note).
- Each program call becomes a binding: the bridge snapshots lossless-JSON arguments and dispatches through the complete guarded tool pipeline — `tools/pre-execute` → guards → `tools/execute` → `tools/post-execute` → `tool/result` — so sandbox policy, approvals, and logging apply to nested calls identically. Sub-call ids are `<parent>:ptc:<n>`. Every sub-dispatch logs a log-only `tool/ptc-dispatch-start`/`tool/ptc-dispatch` event pair carrying name, arguments, and the full rendered result; these events are outside model history.
- Concurrency is bounded, not serialized: consecutive `isConcurrencySafe`-classified calls overlap up to `maxParallelSubCalls` (default 10; `1` restores serial); an exclusive call drains the pool. A failed program is never replayed implicitly because earlier effects may have committed.
- Sub-call `additionalContexts` are deferred through the parent's result, so parent-call/result adjacency in the log is preserved.

Execution substrate ([sandboxed Node decision](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/architecture/2026-09-11-sandboxed-node-ptc-runtime.md); [PTC runtime doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/ptc-runtime.md)):

- Default `per-call` mode: each program runs in one fresh Node process, launched through the same `ctx.sandbox` provider Bash uses, with process lifetime owned by `ctx.subprocess`. An earlier worker_threads design was replaced because a worker isolates JS state but cannot apply the session's OS file policy to direct `node:fs` imports.
- Bindings cross a dedicated inherited binary control channel separate from stdout/stderr; the host bounds frames, queued writes, pending calls, and outstanding argument bytes, and treats all channel bytes as untrusted.
- Result contract: `{ value?, logs[], error? }` resolved as fields, never thrown. Failure kinds are orthogonal: `exception`, `timeout`, `abort`, `worker-exit` (substrate death, e.g. OOM), `invalid-output` (completion value not lossless JSON), `output-limit`, `protocol`, `sandbox-unavailable`. The error message is written to be fed back to the model for self-correction ([PTC runtime doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/ptc-runtime.md)).
- Budgets: default elapsed deadline 120 s, capped at 600 s; the deadline includes runtime setup and nested tool or approval waits. V8 old-generation memory, serialized output, and control traffic have separate bounds. Elapsed time is not a process-tree CPU budget, and the heap limit excludes native allocations — both stated openly as limitations ([sandboxed Node decision](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/architecture/2026-09-11-sandboxed-node-ptc-runtime.md)).
- An opt-in in-memory mode allows disposable cross-call memory; the default stays stateless because cross-call state invisible to the session log would break the "every request reconstructable from the log" guarantee ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md); [best-effort persistent PTC note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/architecture/2026-09-23-best-effort-persistent-ptc.md)).

### 4.1 Code-level additions (verified in the clone)

- The `run_code` schema carries controls the docs pages never mention — the one docs/code gap found: optional `timeoutMs` (emitted only when the runtime exposes a `timeout` descriptor, with the runtime's default and cap rendered into the parameter description) and `sandbox_permissions` plus `justification` (emitted only when the runtime enforces file policy), which request a wider file mode for that one program through the approval service. The rendered tool result appends partial-enforcement warnings and, on denial, escalation guidance: "A sandbox escalation approves this complete program for one execution only … Programs are never replayed automatically." (`packages/core/tools/src/ptc.ts:92-140,286-395`).
- Prompt and enforcement share one predicate: the `tools:ptc-only` prompt section renders the collapse rule through the same `modeFor(scope)` check the executor denies by, so the prompt cannot state a rule the registry does not enforce (`packages/core/tools/src/index.ts:869-888`).
- Schema emission is language-aware at emit time: `resolveFlavor()` reads the mounted runtime so the model-visible `run_code` description always matches the SDK section's language, degrading to TypeScript only on paths no model request reaches (`packages/core/tools/src/ptc.ts:125-140`).
- The Node runtime's shipped defaults, verified in the config schema: `timeoutMs: 120_000`, `maxTimeoutMs: 600_000`, `maxOutputBytes` 64 MiB, `maxOldGenerationSizeMb` 512, `maxMessageBytes` 128 MiB, `maxPendingCalls` 128, `graceMs` 3,000 (`packages/ptc-runtime/ptc-runtime-node/src/config.ts:30-40`).
- A session sandbox-mode change cancels both active programs and calls admitted before launch: each run registers with a per-session `PolicyProcesses` registry that aborts its controller when the policy changes (`packages/ptc-runtime/ptc-runtime-node/src/index.ts:105-130`).
- Programs are wrapped as `async function __dsh_program__() { … }` and passed through `stripTypeScriptTypes` from `node:module`; the elapsed deadline is a plain `setTimeout` that aborts the run controller (`packages/ptc-runtime/ptc-runtime-node/src/index.ts:30-31,153-154`).

Stated costs and risks ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md)): the SDK text can rival the native schemas it replaces (amortized by provider caching); every `run_code` pays a Node process launch plus sandbox setup; a run of exclusive calls still costs its round-trips in sequence; and models may over-expect `Promise.all` parallelism because overlap is limited by per-tool safety classifications.

## 5. Session storage and resume

The session is an append-only `SessionEvent` log; in-memory state is a projection of it ([core doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md)). Durability is a handle-based seam ([persistence doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)):

- The shipped provider stores one file per session: `session.jsonl[.zstd]` (v0) or `session.vN.jsonl[.zstd]` (v1+). Committed generation paths are never renamed, replaced, or deleted; a version bump publishes a new version-named successor file beside the unchanged source, and each migration package owns exactly one `vN → vN+1` step. The current writer format is v4 (`SESSION_FORMAT_VERSION` in `packages/core/session/src/types.ts`); the latest released format is also v4, evidenced by product tag `dsh-v0.2.0-rc.2` ([session-format-status doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/session-format-status.md)).
- Access goes through a `SessionHandle` (`read`/`append`/`flush`/`close`) with single-writer ownership: a second write-open rejects with `SessionAlreadyOwnedError`. `append` is best-effort and may buffer; `flush` is the durability barrier that promises crash survival.
- Events are batched in a bounded write-behind window; the loop runs `session/flush` as the ordering and error checkpoint before claiming the next turn.
- Per-session metadata (format version, cwd, fork lineage `isSeeded`, `parentSession`, `delegationDepth`, `agentPreset`, subagent `origin`) lives in a separate `SessionHeader`, outside the event log, precisely so a resume restores the same toolset and prompt composition that produced the history.
- Crash recovery: persistence never truncates a log crashed mid-turn; it returns the valid contiguous log, discards only a torn physical tail, and durably rewrites any complete records recovered from the torn frame. Resume (the agent loop) then computes `interruptedTurnClosers` — missing tool errors, any open `step/end`, and a synthetic `turn/end { reason: { kind: 'interrupted' } }` — and appends them before publishing the session. `interrupted` is the one turn-end reason no loop emits.
- Fork: `ctx.agents.create({ sessionId, seed, meta: { parentSession, isSeeded: true, inheritedEventCount } })` seeds a child with a completed-turn prefix of the parent's log, marked by a child-owned end-seed marker; resume of a persisted session is `ctx.agents.resume({ resumeSessionId })` ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md); [persistence doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)).
- Search/replay consumers sit above this: `ctx.sessionQuery` provides provider-independent filters and a SQLite full-text index provider over the logical corpus, with per-event surface classification (`current`, `shadowed`, `log-only`) matching what model-history derivation would fold ([session-query doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session-query.md)).
- Each `assistant/message` embeds the exact compact timed stream that produced it, so transcripts, telemetry, and resume all derive from durable settlements; a process loss before settlement leaves no durable attempt stream ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)).

### 5.1 Code-level additions (verified in the clone)

- `SESSION_FORMAT_VERSION = 4` (`packages/core/session/src/types.ts:90`); `TurnEndReasonMap` is a merge-extensible sum type whose `interrupted` and `forked` variants are both documented as never emitted by the live loop (`packages/core/session/src/types.ts:202-233`).
- Fork is a pure function over the source log: `buildForkSeed(events, boundary)` copies the inclusive prefix, appends a child-owned `session/end-seed { inherited: true }` marker at the cut, then closes an open tail turn with cause-`forked` synthetic closers (`packages/core/session/src/fork.ts:21-32`).
- Synthetic closers are deterministic: `openTurnClosers()` scans turn/step boundaries with the same `ToolCallRecovery` the live loop uses, reuses the last real event's timestamp, and continues seq numbering (`packages/core/session/src/repair.ts:53-98`). Synthetic tool-result wording distinguishes `interrupted` ("Its outcome is unknown … retry only if the operation is read-only or idempotent") from `forked` ("The parent session may have completed it after the fork point") (`packages/core/session/src/repair.ts:32-41`).
- Single-writer is a kernel lock, not a convention: the JSONL provider takes a non-blocking `flock(2)` on `session.lock` (POSIX) or a named kernel semaphore (Windows); contention maps to `SessionAlreadyOwnedError`; the kernel releases on holder process death; the POSIX holder verifies the locked inode still matches the lock path because an unlinked-and-recreated lock file carries a fresh inode; there is deliberately no expiry that could expropriate a stalled writer whose resumed appends would tear the log (`packages/session/session-persistence-jsonl/src/lease.ts:1-38`).
- Torn tails are repaired by truncate-plus-rewrite: the zstd reader reports `tornStart`, the backend truncates the torn bytes before the first new append, and durably rewrites the complete events recovered from the torn final frame (`packages/session/session-persistence-jsonl/src/zstd.ts:38-96`; `packages/session/session-persistence-jsonl/src/storage.ts:49-71,318-328`).
- Unknown event types are handled by an `ignorable` marker on the event envelope, not by event-name registration; the generated `KNOWN_SESSION_EVENT_TYPES` list refuses a log containing a non-ignorable unknown type because "silently skipping a required event would reconstruct a wrong session" (`packages/core/session/src/known-event-types.ts:12-19`).
- The in-memory `Session` holds one incremental `SurfaceManager` over the log (`packages/core/session/src/index.ts`), and tool history is itself a projection: `ToolHistoryProjection` folds `request/header` and `developer/message` tool-addition/removal events into the declaration series a route needs, refusing a retained name whose definition changed ("A retained name cannot acquire a different definition without losing prefix reuse") (`packages/core/session/src/tool-history.ts:15-50`).

## 6. Permissions and security boundaries

Three independent enforcement knobs, composed into named presets ([permission-presets doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/permission-presets.md)):

- **Approval** (`ctx.approval`): answers "may this specific action proceed?" through an answerer waterfall. Outcomes are closed: `allowed-once` (the only grant), `rejected`, `cancelled`, `unavailable`. Callers fail closed on everything except `allowed-once`; a missing, throwing, or non-conforming answerer yields `unavailable`. Per-session policy is `ask` or `never`; `never` deterministically rejects without dispatching any answerer and cannot be bypassed even by a later `prepend` answerer. Every ask/decision pair appends log-only `approval/asked`/`approval/decided` audit events that stay out of the model transcript ([approval doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/approval.md)).
- **Sandbox mode** (`ctx.sandbox`): file-effect policy per call — `read-only`, `workspace-write` (workspace root plus backend temp area), or `danger-full-access` (bypass). Enforcement completeness is a reported fact (`full`/`partial`); older Landlock ABIs and Windows ACL gaps are documented `partial` cases. Denial signatures are backend-specific dialects (EROFS under bwrap, EACCES under Landlock, EPERM under Seatbelt), matched per backend rather than as a cross-backend union; runner-failure rules distinguish "sandbox failed to launch" from "sandbox correctly blocked the command". Silent unconfined passthrough for a confined policy is never legal ([sandbox doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/sandbox.md)).
- **Permission presets**: shipped `workspace-write` (workspace-write + ask) and `danger-full-access` (danger-full-access + never), plus a session-only Auto integration; `custom` is a derived display value, never a switch target ([permission-presets doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/permission-presets.md)).

PTC inherits all of it: nested tool calls re-enter the full pipeline including `tools/pre-execute` approvals, program execution is confined by the same OS sandbox as Bash, and the trust posture is explicit — program success does not prove full enforcement, and the `isolation` descriptor "describes the substrate without claiming security" ([PTC runtime doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/ptc-runtime.md); [sandboxed Node decision](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/architecture/2026-09-11-sandboxed-node-ptc-runtime.md)). The project's own SAFETY notice states it has not undergone a security audit, must not be treated as production-ready, and should run with least privilege in a disposable VM/container ([SAFETY.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md)). The web server adds its own boundary: loopback-only by default, a launch-token exchange and signed cookie for every API method and WebSocket, a Host/Origin fence, opt-in TLS with no ACME, and rejection of wildcard binds ([web-app README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/README.md)).

### 6.1 Code-level additions (verified in the clone)

- Approval state is log-derived with no in-memory authority: the effective policy scans the log backwards for the last `approval/policy` event, `setApprovalPolicy` writes a new event, and a policy switch also injects a model-visible user message stating the change (`packages/interaction/user-approval/src/index.ts:184-195,252-259`).
- The `never` gate sits inside the service's `decide()` before the waterfall, with an explicit code comment: a listener registered with `prepend: true` would sit ahead of any gate listener, so only the service's own request path can guarantee the deterministic reject (`packages/interaction/user-approval/src/index.ts:267-275`).
- Containment is explicit: the dispatch enters the promise chain before invocation so a synchronously throwing answerer lands in the same rejection path; a throwing or non-vocabulary answerer normalizes to `unavailable` ("a throwing answerer must fail the QUESTION closed, not the caller's tool call open"); an abort wins the outcome race as `cancelled` and a late answer is discarded by construction (`packages/interaction/user-approval/src/index.ts:267-307`).
- Approval asks must be turn-enclosed: `request()` throws outside an open turn because "a bare event between turns is crash-tail garbage on reload" — the turn-enclosure invariant extends to auditing (`packages/interaction/user-approval/src/index.ts:84-91,215-223`).
- The sandbox runner chain is selected by platform first, probes second: Linux prefers `bwrap` (its mount profile is closest to the mode vocabulary) then the Landlock launcher; darwin's `seatbelt` is a sole candidate selected without any probe; Windows is the ACL restricted-token runner, sole candidate, whose execution-time refusal fails closed through the `windows-acl-run:` stderr signature and exit 127 (`packages/sandbox/sandbox-local/src/index.ts:151-165`).
- Enforcement honesty is literal in the tables: `bwrap`/`landlock`/`seatbelt` claim `full` as a profile fact; `windows-acl` claims `partial` with named reasons (NTFS hard links alias a granted workspace file to a path outside it, reads stay unconfined, an AppContainer-ACL'd tree is unreadable to the Low-integrity child); the Landlock launcher additionally self-reports partial enforcement on older ABIs at every confined run (`packages/sandbox/sandbox-local/src/index.ts:170-191`).
- Denial dialects and runner-failure rules are per-backend constants: `read-only file system` (bwrap), `permission denied` (landlock), `operation not permitted` (seatbelt), four Windows spellings; Landlock's runner rule is exit-gated on 125 with its "partial enforcement" line excluded as informational, so a confined command that merely prints a signature is never misclassified as "the command did not run" (`packages/sandbox/sandbox-local/src/index.ts:196-226`).
- The Windows runner receives two SIDs: a per-workspace write SID whose root ACE materializes once per workspace and stands (cross-session O(1) reuse), and a per-session random private temp directory with its own derived capability, revoked on dispose (`packages/sandbox/sandbox-local/src/index.ts:8-21`).
- The Seatbelt SBPL profile and the in-process filesystem fence share one `writableRoots()` helper so the kernel grant and the fs fence cannot drift apart (`packages/sandbox/sandbox-local/src/profiles.ts:44-57`).

## 7. What baton-cli should copy

- **Named runtime modes as first-class compositions.** The `standard`/`ptc`/`minimal` presets are pure data: a plugin list, a persona prefix, per-plugin config, isolation realms. baton-cli's equivalent — a standard mode with the full toolset, a minimal mode with editor + shell + compact prompt, a PTC mode — can be a static composition table rather than a framework. The `minimal` preset is direct precedent for baton-cli's minimal mode: no text file tools, shell-only file access, fixed persona, no runtime-context block ([minimal preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/minimal.patch.yml)).
- **PTC batching for a minimal toolset.** PTC's core value for baton-cli is that a minimal toolset (read/write/edit/shell + orchestrator inbox) stays minimal while gaining loop/branch/fan-out composition: the model writes a program calling `tools.*` bindings, and only printed/returned values re-enter context. dsh's contract details are worth copying wholesale: required `{ code, description }` parameters, `Promise.all`-only-for-concurrency-safe-calls stated in the SDK text, log-only sub-dispatch events with parent-child call-id correlation, fresh-process execution with an explicit failure taxonomy including `output-limit`, and "a failed program is never replayed" ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md)).
- **Turn-enclosed event log with interrupted-turn repair.** The invariant "model-visible means logged", the synthetic `turn/end { kind: 'interrupted' }` appended at resume, header metadata carrying the composition (`agentPreset`, cwd, lineage) so a resume restores the same toolset, and immutable versioned generation files with per-step adjacent migrations are all directly applicable to baton-cli's session format and the orchestrator's need to resume/fork a seat at turn boundaries ([persistence doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)).
- **Fail-closed approval with auditable outcomes.** The closed outcome set (`allowed-once`/`rejected`/`cancelled`/`unavailable`), the deterministic `never` policy, and log-only audit events per ask are a small, complete design ([approval doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/approval.md)).
- **Honest sandbox reporting.** Reporting enforcement completeness (`full`/`partial`) and backend-specific denial signatures rather than pretending uniform isolation is a pattern baton-cli can adopt cheaply even with a single sandbox backend ([sandbox doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/sandbox.md)).
- **Cache-stability as a design rule.** Keeping the tool catalog identical across modes so the request prefix stays cacheable, and lexicographically sorted SDK sections for byte-stable prompts, are cheap wins for baton-cli's prompt assembly ([standard preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/presets/standard.patch.yml); [PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md)).

## 8. What fits poorly for a Bend2-native harness

- **The Cordis microkernel.** Services, fibers, waterfalls, scoped dispatch, effect unwinding, HMR reload, and three-event-domain taxonomy exist to support a ~400-package plugin ecosystem. dsh's own docs require a primer and tutorial to modify anything under `packages/` ([architecture doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)). baton-cli's stated scope — minimal toolset, async streaming, orchestrator protocol — needs none of that; a fixed module graph in Bend2 with explicit seams is the cheaper equivalent.
- **Waterfall event interception.** Most extension points are listener waterfalls with `next()` delegation and ordering-dependent semantics; dsh itself documents the ordering hazards (e.g., it rejected an add-on PTC consumer precisely because a transform would depend on listener order) ([PTC agent note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-06-15-ptc.md)). A minimal harness should prefer explicit, statically known hook points.
- **The plugin distribution surface.** npm bundles, pnpm-managed profiles, peer-range enforcement, version exemptions, and a model-facing `plugin_manager` tool that can install packages with build scripts ([tool catalog](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md); [CLI README](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md)) is a large security and maintenance surface that a self-contained Bend2 harness does not need.
- **Format-versioning machinery at this scale.** v0–v4 with per-step migration packages, bilingual release records, and catalog-generator verification ([session-format-status doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/session-format-status.md)) is appropriate for a shipped product with installed users; a new harness can adopt the immutable-generations idea with a single current version.
- **Per-call fresh-process PTC.** The 120 s default / 600 s cap elapsed deadline, Node-process launch plus sandbox setup per `run_code`, and deferred CPU/RSS questions are acknowledged costs ([sandboxed Node decision](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/architecture/2026-09-11-sandboxed-node-ptc-runtime.md)). A Bend2-native harness with native concurrency can consider in-process structured evaluation with host-owned bindings, but must re-derive the confinement story — dsh's decision record shows why worker/isolate schemes fail the OS-policy test.
- **Remote sandbox integration cost.** The E2B removal shows the real cost of remote execution worlds: descriptor control channels, bounded retention, channel closure, and cancellation cleanup turn a provider into a transport project. A minimal harness should ship local confinement first and treat remote execution as an out-of-tree concern ([E2B removal note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/simplification/2026-09-11-remove-e2b-providers.md)).

## 10. Core architectural concepts

Six concepts make this harness's approach coherent. Each is grounded in the code paths analyzed above.

1. **The log is the program.** The session is an append-only, turn-enclosed event stream, and everything else is a fold over it: model history (`session.deriveMessages()`, `packages/core/agent-loop/src/agent.ts:688`), pending input (`agent/inbox/spliced` events, `packages/core/agent-loop/src/inbox.ts`), tool declarations (`ToolHistoryProjection`, `packages/core/session/src/tool-history.ts`), approval policy (`packages/interaction/user-approval/src/index.ts:252`), and turn/step boundaries (`turnBoundaryProjectionDefinition`, `packages/core/agent-loop/src/index.ts:57-95`). This is why resume, fork, search, and UI replay share one implementation and why "model-visible means logged" is enforceable rather than aspirational. The design optimizes for reconstructability: any consumer can rebuild any state from seq 0, and a write path that appends an unbalanced event is a named bug the repair layer can close.
2. **Turn enclosure as the atomicity unit.** `turn/start`…`turn/end` bracket all durable side effects. The loop closes every exit path with a reason in a `finally` (`packages/core/agent-loop/src/agent.ts:384-391`); crash repair synthesizes closers in the same shape as live repair (`packages/core/session/src/repair.ts`); fork reuses the identical mechanism with a `forked` cause (`packages/core/session/src/fork.ts`); even the approval audit pair must be turn-enclosed (`packages/interaction/user-approval/src/index.ts:217`). Crash recovery and fork are the same operation at different causes.
3. **Patches as the composition language; seams as the extension surface.** Product behavior is data: preset YAML inserts plugin rows, patches replace whole configs by id, capabilities swap at three-role seams. The cost is visible in the loop — assembly listeners own the integrity of any rewritten protocol — and the counter-move is visible too: the PTC collapse rule is rendered from the same predicate the executor denies by, so prompt and enforcement cannot drift (`packages/core/tools/src/index.ts:869-888`).
4. **Bounded concurrency as a portable contract.** One classification (`isConcurrencySafe` → `executionMode`) drives three schedulers: the native loop's rolling pool (`packages/core/agent-loop/src/tool-calls.ts`), the PTC sub-dispatch lane (`packages/core/tools/src/ptc.ts:407-510`), and tool binding parallelism. Ordered commits through a head-of-line cursor keep the log model-ordered; exclusive barriers hold through post-execute; concurrency policy lives in tool metadata, never in callers.
5. **Fail closed, report honestly.** Every boundary normalizes the unknown into a closed vocabulary plus a reported fact: approval normalizes rogue or throwing answerers to `unavailable`; the sandbox reports `full`/`partial` enforcement and per-backend denial dialects; PTC resolves program failures as orthogonal result fields and never replays a failed program. The recurring pattern is a closed outcome union plus a descriptor carrying what actually happened, never an exception path and never a silent fallback.
6. **Cache-aware prompt assembly.** The request prefix is treated as an asset: request headers record change reasons (`initial`/`resume`/`series`/`change`, `packages/core/agent-loop/src/agent.ts:635-651`), tool-catalog changes are admitted as `developer/message` deltas (`packages/core/agent-loop/src/agent.ts:652-666`), the runtime-context snapshot travels after retained history (`packages/core/agent-loop/src/runtime-context.ts`), the PTC SDK section is lexicographically byte-stable, and the tool catalog is deliberately identical across modes so the schema block never changes. The harness treats provider prompt caching as a first-class design constraint.
